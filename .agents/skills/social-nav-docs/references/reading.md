# 外部范文与写作方法

这些参考用于学习表达和组织方式。按当前问题选读一篇即可，不要求每次联网、通读全部资料或复制整套文档。下列摘要足以支持普通修改；需要理解完整写法时再打开原文。

项目技术事实仍以代码、配置和验证记录为准。外部示例中的架构、参数和操作不构成本项目的实施要求。[项目改写示例](examples.md)用于说明这些方法怎样应用到 Social-Nav。

## 中文概念解释：Vue 响应式基础

来源：[Vue 中文文档：响应式基础](https://cn.vuejs.org/guide/essentials/reactivity-fundamentals)。

- **重点阅读**：`ref()`、为什么要使用 ref、DOM 更新时机。
- **借鉴**：从最小用法开始，解释读者能观察到的行为，再展开原理和限制。示例紧跟解释，深入机制另有入口。
- **适用于项目**：共享内存、地图关联、身份生命周期等技术专题。先说明数据如何被使用，再解释内部机制。

例如，介绍共享缓冲时，可以先讲“生产进程写入一帧数据，读取进程处理完后释放引用”，再解释槽位为什么要等待读取方释放。是否以及怎样实现这一过程，须以项目代码为依据。

## 中文操作说明：Python 虚拟环境和包

来源：[Python 中文教程：虚拟环境和包](https://docs.python.org/zh-cn/3/tutorial/venv.html)。

- **重点阅读**：概述、创建虚拟环境。
- **借鉴**：先用依赖冲突解释操作目的，再给步骤，并说明执行后目录、解释器或终端提示会发生什么变化。
- **适用于项目**：开发指南、环境准备和操作速查。

例如，解释检测环境与系统 ROS 环境时，先说明为什么需要区分解释器，再告诉读者如何选择，最后给出命令和检查办法。本项目已有环境安排仍按开发指南及本机记录执行，不照搬教程中的版本或安装命令。

## 状态与失败处理：ROS 2 Managed nodes

来源：[ROS 2 设计文档：Managed nodes](https://design.ros2.org/articles/node_lifecycle.html)。

- **重点阅读**：Life cycle 中的状态图、状态含义和允许的转换。
- **借鉴**：先用图说明状态之间的关系，再交代每个状态能做什么、由什么事件离开、失败后进入哪里。
- **适用于项目**：Agent 任务状态、定位失效、取消和停车流程。

例如，说明取消任务时，应分别写清“已请求取消”“已收到回执”“已确认停车”的判断依据，再按实际代码说明它们之间如何转换。该来源是历史设计文档，只参考写法，不据此引入 ROS 2 或改变项目通信方式。

## 日常审校：Google 技术文档风格指南

来源：[Google developer documentation style guide：Highlights](https://developers.google.com/style/highlights)。

- **重点阅读**：语气与内容、主动语态、条件与指令的顺序、描述性链接文字。
- **借鉴**：明确谁执行动作；先说明条件，再给操作；链接文字交代目标内容。
- **适用于项目**：日常说明、操作步骤和审校。

例如，用“需要查看当前 RGB 时，启用对应的图像记录选项”组织说明，再按项目实际入口补充参数。中文不套用英语的拼写、大小写或标点规则，也不把专业说明强行改成聊天语气。

## 内容归属：Diátaxis

来源：[Diátaxis 文档体系](https://diataxis.fr/)。

- **重点阅读**：教程、操作指南、技术参考和原理解释的区别。
- **借鉴**：根据读者是在学习、完成任务、查字段还是理解原因，决定正文需要什么内容。
- **适用于项目**：判断一段文字应进入系统方案、操作速查、接口约定还是技术专题。

例如，同一地图功能的使用命令进入操作速查，构建原理进入技术专题，字段定义进入接口说明，必要处互相链接。沿用本项目已有目录和维护职责，不为了套用分类重建文档树。

## 使用反馈

优先记录用户认可的项目改写实例。只有实际使用暴露了新的表达问题时，才补充参考或规则；不要不断扩充书单。引用原文时保留出处，用自己的话说明借鉴点，避免复制长段内容。
