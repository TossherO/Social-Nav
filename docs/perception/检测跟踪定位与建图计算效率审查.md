# 检测、跟踪、定位与建图的计算效率审查

本文依据 2026-11-24 的项目工作树，审查从传感器输入到行人轨迹、定位结果、局部环境图和导航工作栅格的计算过程，也覆盖三维建图与离线补图。在线部分关注下游多早能拿到有效观察，离线部分关注用同一批证据生成同等地图需要多久。路径搜索、轨迹生成和运动控制算法不在本次范围内。以下均为优化建议，本次未修改实现、重新测速或开展实机实验。

## 建议先做哪些

| 优先项 | 为什么值得先做 | 第一项能说明问题的检查 |
| --- | --- | --- |
| 在线三维检测 | 在以往轮椅测量中占一个雷达周期的很大一部分。当前代码可确认有重复点云指纹、临时数组和 GPU 等待，但还不知道各自占多少 | 在同一组扫描上分别计时三帧拼接、上卡、网络、候选筛选和跟踪，同时记实际点数、候选框数与被替换的扫描数 |
| 定位长尾 | 连续局部位姿和楼层地图配准由两个执行线程产生。少数很慢的子图切换就可能让后端结果到达时超龄 | 按同一源扫描关联排队、子图准备、匹配结束和关联发布，分开首建、切换、稳定行驶和质量门控拒绝 |
| 局部图发布与导航地图投影 | 环境图已大量使用 CUDA。现有车载证据指向局部几何投影，源码另显示几个 CPU/GPU 同步点和可选消费者的重复搬运 | 以同一张地图测设备就绪、主机必要字段就绪与首次消费。对投影再记候选格、实际相交格和变更格数 |
| 离线固定图配准与静态地面估计 | 补图中有只消费定位结果却启动整套感知导航的阶段。另有只抽部分扫描却先解压全部扫描、按多个位姿反复扫全图点云的路径 | 分别统计每个工作流启动的模块、实际解压次数和每个地面拟合位置检查的点数，再比较相同证据生成的产物 |

**已有证据。** 2026-11-08 轮椅端 RTX 4060 Ti、约 10 Hz 雷达、三帧检测、7.5 Hz 地图和 RViz 的历史记录中，检测与跟踪完整调用 P50/P95 为 76.66/115.54 ms，前台定位会话为 7.11/9.94 ms。后者不包含后台 ROLL 从排队到发布的完整时延。11 月 22 日同一车载机的封存查询中，新观察工作图准备的中位耗时为 19.89 ms，其中局部投影占 13.40 ms，整图复制和逐格比较各约 0.60 ms。这两批记录的输入、日期和负载不同。[项目现有测量及条件](../推理速度记录.md)

**服务器短片段。** 此前 RTX 3090 服务器 对一楼 `2026-10-23-11-19-34.bag` 前约 8 秒的交互回放采用 0.8 倍速、三帧 FP32、18 m 窗口、5 Hz 地图，保留 ROS 显示发布和规划记录，使用一楼人工驾驶预设，期间暂停选点。摘要记录了 81 帧输入，主进程处理 72 帧，替换 9 帧，发布 31 张地图。检测跟踪墙钟 P50/P95 为 58.3/112.2 ms。66 次 ROLL 处理中，子图阶段 P50 低于 0.01 ms、P95 为 274.3 ms。31 张图为独立安全等主机消费者合包下载约 17.1 MB，建图异步任务另有约 3.95 MB 的主机输入复制。这里的字节数是整段累计。片段含冷启动和暂停，可用于定位耗时环节，稳定行驶时的延迟还需车端测量。

## 传感器输入、传输与调度

直接运行时在系统 Python 输入进程解码雷达与 IMU，运行 FAST-LIO，并向独立安全进程送位姿。主进程从共享槽读取原始扫描做检测跟踪，局部建图使用去畸变扫描、位姿和同帧人物结果。常规导航的扫描接收和地图线程各自最多保留一个执行中任务和一个最新待处理任务。扫描归档、完整观察记录和 Agent 观察等模式会选择同步地图路径。性能对照必须记下实际走的是哪一条。[运行入口](../../runtime/__main__.py) · [输入进程](../../runtime/input_worker.py) · [扫描调度](../../runtime/scan_inbox.py) · [地图调度](../../runtime/environment.py)

| 位置与现状 | 建议与判断依据 |
| --- | --- |
| `pointcloud_fields` 已按字段类型、字节序和行步长提供 NumPy 视图。`bag_observations` 拼一次原始 XYZI，`rs16_preprocess` 又为定位组织 XYZ、强度和点时间 | 在同一消息内共享字段解析，消去 `column_stack(...).astype(...)` 中可避免的第二次复制。定位按原始索引采样时可提前缩小几何计算范围。用有行填充、无效点及时间边界的输入比对原始检测点顺序、定位保留点、逐点时间和扫描起止时间。原始检测云与去畸变云分别有消费者。[组帧](../../perception/sensors/observations.py) · [点云视图](../../perception/sensors/pointcloud.py) · [原生接口](../../perception/mapping_localization/native.py) |

| 同帧人物归属决定哪些端点写入背景，建图依赖检测输出。相邻扫描的解码、设备传输和上一帧地图计算有机会重叠 | 优先重叠独立的准备工作，保留单一地图写入者、三帧检测历史和卡尔曼跟踪的时间顺序。检查 `received/replaced/published` 和障碍首次出现时间。若 Agent 观察的同步模式造成积压，可试按同一源时间和代次配对已封存结果，验证完整观察与归档的覆盖率。给旧人物数据换上新扫描时间会破坏动态点剔除。[地图提交与观察配对](../../runtime/__main__.py) |

## 行人检测与跟踪

公共配置使用三帧 VoxelRCNN FP32 和 CPU 跟踪关联。在线检测复用了 `training/simpledet3d` 下的模型与 CUDA 扩展。建议以运行摘要中的实际模型、精度、配置摘要及扩展为准。已有车端短段曾观察到 FP16 没有提速，整链表现还受 CPU 调度影响。[推理配置](../../perception/detection_tracking/configs/inference.json) · [检测参数](../../perception/detection_tracking/configs/detector.yaml) · [历史对照](../archive/感知导航现场历史.md)

1. **同一帧的指纹只需计算一次。** `CausalSweeps.prepare` 对原始点计算 SHA-256 并存入检测上下文，`PerceptionPipeline.step` 在生成最终结果时又调用 `frame.input_fingerprint()`。在一次成功调用中复用前者可消除一次完整点云遍历。还应分别覆盖单帧、三帧、定位降级、异常和使用其他检测器的分支，检查输出与历史记录中的指纹相同。现有内部 `timing_s.pipeline` 在最终结果组装前结束，会漏记第二次计算。[三帧输入](../../perception/detection_tracking/inference/detector.py) · [输出组装](../../perception/detection_tracking/inference/pipeline.py)
2. **缩减三帧拼接的内存流量。** 当前先剔除无效点和自车区域，对每份历史扫描复制、变换并写入时间差，再拼接并打包单样本批次。可合并当前帧筛选掩码，一次分配合并后的缓冲，按切片写入各帧，随后测是否值得让部署入口直接生成单样本布局。保留点序、强度归一化、相对位姿和时间差，定位失效时仍清空历史。动态体素化已在 GPU 执行。若体素化本身占比高，再研究将去重、排序和每体素最多 20 点的筛选合为分段处理，核对拥挤体素最终保留哪些点。[检测输入与设备提交](../../perception/detection_tracking/inference/detector.py) · [动态体素实现](../../perception/detection_tracking/training/simpledet3d/simple_det3d/models/vfe.py)
3. **分开测网络、候选区域精修和非极大值抑制（NMS）。** 检测头逐帧从配置构造设备常量，精修头反复生成 6 × 6 × 6 网格的 216 个采样坐标。两者适合按设备、类型缓存，只广播每个候选所需的结果。精修耗时应按实际传入的候选数统计。当前检测头可直接写入 `rois`，后面的 proposal 层会提前返回，单看精修配置里 100 个候选的上限会低估工作量。旧 `nms_gpu` 会分配显存，将成对抑制掩码同步复制回 CPU，再由 CPU 挑索引。这笔传输没有完整反映在最终检测框的下载计数中。先记录候选数、掩码字节及同步时间，显著时再尝试复用空间或设备端选择，并比对等分、阈值附近及重叠人物的保留顺序。[检测头](../../perception/detection_tracking/training/simpledet3d/simple_det3d/models/center_head.py) · [候选区域精修](../../perception/detection_tracking/training/simpledet3d/simple_det3d/models/voxel_rcnn_head.py) · [NMS 原生实现](../../perception/detection_tracking/training/simpledet3d/simple_det3d/ops/iou3d_nms/src/iou3d_nms.cpp)
4. **按候选对数选择跟踪计算方式。** 当前先做中心距离门控，只对通过的检测框与轨迹对计算旋转框代价。CPU GIoU 分支还涉及多边形、凸包和双轮匈牙利匹配。先记录检测数、活跃轨迹数、通过门控的对数和两次匹配的耗时。可以每框只生成一次角点，拥挤场景再测批量原生几何或按互不相连的门控分组求解。已有 Triton 关联后端会上传框与索引、下载代价，最后仍由 CPU 分配。小人群应保留 CPU 对照。跟踪结果还逐帧将框、协方差和可用速度转成 Python 列表，并由主循环同步写入人物 JSONL，可把记录耗时单列。在多人时若序列化占比明显，可用有界的后台写入并核对顺序、记录数和失败报告。评价时比对高低分两轮分配、漏配、轨迹断裂与身份切换，保留定位失效后的轨迹重置。[跟踪器](../../perception/detection_tracking/inference/tracker.py) · [CPU 关联](../../perception/detection_tracking/inference/association.py) · [GPU 关联](../../perception/detection_tracking/inference/association_cuda.py)
5. **有 RGB 消费者时单独核算二维分支。** 相机配对、二维检测和三维轨迹投影只在相应任务或记录模式下发生。局部决策已有预热的 TensorRT 二维后端。可统计同一 RGB 被多个窗口重复选中的比例，只缓存相同图像、模型和预处理下的二维框。内参、三维轨迹、观察时间和先前关联变化时重新配对。多人时可预计算像素框中心和尺寸，减少两轮匹配重复工作。记录相机等待、图像复制和结果应用年龄。车载跟随回放已有工作线程变快、应用年龄 P95 反而变大的例子。[相机配对](../../runtime/follow_camera.py) · [图像准备](../../decision/vlm/image_inputs.py) · [图像关联](../../perception/detection_tracking/inference/rgb_association.py) · [跟随回放对照](../推理速度记录.md#t2-本地身份匹配)

## 在线定位与三维建图

FAST-LIO 前端逐扫产生连续局部位姿。ROLL 后台在固定楼层图上匹配，或在建图模式维护关键帧与回环。实时固定图匹配可替换排队的旧任务，固定图 bag 回放则可能主动等后端消化队列。固定图定位不执行建图的图优化。计时应分别看前端返回、后台匹配、配准源时间和下游接纳时刻。[定位会话](../../perception/mapping_localization/runtime.py) · [传感器入口](../../runtime/input_worker.py) · [ROLL 原生入口](../../perception/mapping_localization/native/roll.cpp)

| --- | --- |

## 实时环境图与导航用地图

这里有三个不同的计算范围。在线几何在随车滚动窗口中更新，公共配置为 18 m、0.10 m 分辨率，即 180 × 180 格，最多使用 5,000 条自由射线。导航支持在有效楼层关联下从静态资产取得车旁依据，配置半径为 3.5 m。全局导航工作图则使用楼层加载时确定的固定裁剪范围，参考观察将局部证据投影到其相交部分。三处的坐标、有效期和来源约束不同。[环境配置](../../perception/environment/configs/environment.yaml) · [环境图机制](技术实现-环境地图与场景表示.md) · [固定窗口](../../perception/environment/storage.py)

1. **先减少地面与人物处理中的重复遍历。** 有效地面帧的 `_plane_ground` 分别求更新前后的地面支撑，旧结果主要用于在本帧采样位置判定冲突。可先计时，尝试只提取旧场在这些格点的支撑值，验证与当前最近有效地面及半径规则等价。地面拟合已限制样本数并复用候选。`point_owners` 对每个人处理整帧点云，可先用保守的轴对齐外接框或一次空间分桶缩小候选，再做原旋转框和连通性判定。CUDA 的人物列归约还会再过一次体素，可测能否随原有投影完成。无人帧仍须处理旧人物证据到期。验收近人遮挡、墙边人群、斜坡、地面冲突和近场历史自由的来源时间。[地面与滚动窗口](../../perception/environment/layers.py) · [地面拟合](../../perception/environment/ground.py) · [人物点归属](../../perception/environment/person_objects.py) · [设备投影](../../perception/environment/native/local_view.cuh)
2. **先量端点上传和同步等待，再决定哪些计算留在 GPU。** 一份扫描会为原生体素证据上传浮点数端点，为局部投影准备双精度输入，在有静态支持时还会上传筛选后的端点。原生默认流会返回体素计数、近场统计等小结果，主机可能为少量字节等待前面的整段设备工作。可让同一地图任务持有一份端点缓冲，在设备上生成各分支的视图或索引，并合并可以同时读取的摘要。保留格边界舍入、人物归属、超预算撤图和时间顺序。当前地面冲突已编码进支撑数据，还可测是否能在设备上派生同一布尔层，省去单独上传。[原生体素更新](../../perception/environment/native/occupancy_cuda.cu) · [局部投影](../../perception/environment/cuda_view.py) · [导航支持核](../../perception/environment/support_cuda.py)
3. **把静态资产缓存和有时效的局部历史分开。** `NavigationSupport.reset` 在关联失效、代次变化等情况下同时清理历史和静态 GPU 缓存。下次有效时将原图的占据、地面、地面支撑、时间四层堆成双精度数组再上传。先数每次重关联的上传字节、等待和显存峰值。若明显，可按静态资产内容摘要与设备保留只读层，并按原生类型存储类别和掩码。局部命中历史仍按会话重置，源时间保持原精度。楼层切换需释放旧资产或限制缓存上限，恢复关联前不能引用旧楼层的自由支持。[缓存与重置](../../perception/environment/support.py) · [几何和关联核验](../../perception/environment/navigation.py)
4. **优先优化局部证据投影的内层。** `reference_overlay` 已将计算限在局部窗口投影的包围盒，筛过可能占据和可能空闲的格子后才做精确相交。持续障碍记忆和先验修订也会计算变换和格间重叠。可先复用同一观察、变换和栅格布局的目标索引与格中心，再将重复分配 NumPy 临时数组的相交循环做成原生 CPU 批处理。历史修订、当前覆盖和持续障碍各有不同的边接触、人物排除、时间及撤销条件。用旋转网格、格边恰好接触、半开门和行人离开后重扫逐格验证。只有额外传输也计入后 GPU 仍占优，才值得迁移。[局部投影](../../navigation/planning/overlay.py) · [先验修订](../../perception/environment/changes.py) · [持续更新的入口](../../navigation/planning/reference.py)
5. **把全图工作留给真正需要它的产物。** 工作图已裁剪并复用内容相同的代价图，距离变换只在空闲包围盒及必要边缘内计算。`ReferenceObstacles.update` 在保留障碍集合变化时仍对整个工作图重列有效索引，可在大楼层且障碍稀疏时比较只维护增删格集合并按确定顺序导出。局部窗口的历史自由已使用分块保存，若热点是每帧 `np.indices` 和坐标变换，可先缓存相同形状的格中心偏移。两者均应验证撤销、窗口移动和关联重置。[代价栅格](../../navigation/planning/costmap.py) · [持续障碍](../../navigation/planning/overlay.py) · [历史自由](../../perception/environment/free_memory.py)
6. **区分必要主机输出和可选显示。** `DeviceGridSnapshot.materialize` 已按消费者选字段，在 GPU 合包后一次下载。独立安全需要主机数据并独立核验。显示、记录和诊断还可能对同一快照另行下载。可以按消费者记字节，复用本次租约内已经取得的同一组主机字段。`layer_binding` 已支持对真正不可变的静态字节缓存摘要，普通 NumPy 只读标记和共享槽不能据此跨代次跳过验真。RViz 当前会将主占据层转 Python 列表，显示叠层还会生成着色点云。可试兼容 ROS 序列化的连续字节或延迟生成无订阅的昂贵显示层，同时保留晚订阅、清图和暂停画面。交互脚本的 `--no-rviz` 只关 GUI，仍会启用显示发布及规划记录。纯计算对照应从直接入口关闭相应消费者。[设备快照](../../perception/environment/device.py) · [场景核验](../../perception/environment/scene.py) · [图层摘要](../../perception/environment/context.py) · [显示发布](../../perception/visualization/runtime.py) · [交互入口](../../runtime/interactive.py)

7. **单独测首次加载和换层的内存与时间。** 固定导航窗口是完整静态图的只读切片。加载时仍会校验整个 `layers.npz`、解压各层并建立不可变的主机数组，安全进程和参考工作进程也会从资产加载。三维定位图有自己的关键帧加载过程。可分开测文件读取、解压、摘要、进程驻留内存和首个有效地图发布，比较冷启动与文件系统已有缓存的换层。如果主要成本来自多个进程重复解压，可试按源内容摘要生成一次只读、可内存映射的派生数组。每个消费者仍核验源资产与布局，只读共享数据的生命周期应跨越最后一个使用者。此项主要改善加载和内存占用。[静态资产](../../perception/environment/storage.py) · [图层读取](../../perception/environment/layers.py) · [独立安全加载](../../runtime/safety.py) · [参考工作进程](../../navigation/planning/runtime.py)

**暂缓重写的部分。** 11 月 22 日车载回放中，全量三维准备、更新和体素投影合计约 1.12 ms。测试的线性 CUDA 距离变换平均 0.218 ms，原实现为 0.104 ms。地面支撑缓存在 309 次非空查询中只命中 33 次，距离场所需的二维掩码也很少可跨帧复用。窗口原点不变时跳过四个地面数组搬移已实现。当前建议保留这些实现。换窗口大小、分辨率或体素密度导致耗时结构改变时再测。局部改动可能改变远处格子的距离或连通状态，增量算法需要与完整输出对照。[车载回放记录](../推理速度记录.md#二楼导航优化回放)

## 编译、并行与验证顺序

**编译应选具体热点。** 定位主干已经是 C++、Eigen、PCL、OpenMP 和 CUDA，检测主干也有稀疏卷积和自定义算子。若瓶颈是 NumPy 投影的循环或检测关联的多边形计算，可先用原生 CPU 实现作同输入对照。若瓶颈是固定形状的稠密检测子网，再单独试编译或降低精度。动态体素数、候选数量、掩码回读以及自定义算子会影响整网编译的收益。编译实验要记录实际 Release 参数、目标 CPU/GPU 和二进制来源。比较不同优化等级或链接时优化（LTO）时，保留 NaN、阈值与浮点边界的语义。定位线程数也应在检测和地图同时运行时比较。[定位构建配置](../../perception/mapping_localization/native/CMakeLists.txt) · [构建入口](../../perception/scripts/build_runtime.sh)

**GPU 并行应验证实际使用的流。** 旧 NMS 和部分 PointNet2 查询的原生 CUDA 启动没有显式传当前 PyTorch 流。仅在 Python 外层新建 stream，可能引入默认流等待或依赖错误。可对已确认的传输热点测试固定容量的页锁定缓冲、异步复制和就绪事件，先核对每个原生算子的设备与 stream，再让独立工作重叠。发布后的张量和主机槽须等全部消费者释放后才能改写。独立安全进程继续在 CPU 上核验输入，GPU 不可用时应保留其停车判断。[NMS 核](../../perception/detection_tracking/training/simpledet3d/simple_det3d/ops/iou3d_nms/src/iou3d_nms_kernel.cu) · [体素查询核](../../perception/detection_tracking/training/simpledet3d/simple_det3d/ops/pointnet2/pointnet2_stack/src/voxel_query_gpu.cu) · [NVIDIA 异步复制与重叠条件](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#asynchronous-and-overlapping-transfers-with-computation)

1. **在车载机上固定一组输入。** 选短的空走廊、多人遮挡或交叉、转角或子图切换片段，优先沿用已有现场袋和对应楼层地图。固定初始位姿、地图与目录、模型、线程、回放速率、窗口和地图频率。按问题选常规最新帧模式或归档模式，同组 A/B 保持一致。单列冷启动、稳定段、丢定位与重获段。查看显示开销时才切换显示和记录选项。
2. **一张表把处理耗时和数据年龄分开。** 用 `--trace-timing`、`timing.jsonl`、`timing_input.jsonl`、`summary.json` 和 `python -m runtime.timing_report <run目录>` 按源扫描配对。记录 CPU 墙钟、CUDA event、每个消费者的传输字节、队列等待与替换、有效发布率和源观察首次使用年龄的 P50/P95。在样本少时列出最慢的具体扫描。当前报告中的首次控制周期和独立安全首次选图可能随后提前退出，要另记首次真正进入几何检查的时刻和样本数。记录总传输字节时区分 H2D、D2H、D2D 与主机复制，现有 `transfer_calls` 统计的是按消费者归集的次数。异步各段的 P95 分别解释。[计时实现](../../runtime/metrics.py) · [汇总口径](../../runtime/timing_report.py)
3. **用相同证据检查结果质量。** 等价优化逐帧比检测输入指纹、候选、轨迹分配、定位关联，以及地图的占据、未知、自由、地面支持、来源时间和动态障碍撤销。未运行某帧和运算结果不同分开统计。涉及数值精度、近邻索引或并行归约时，另设容差并用有标签的多人片段核对漏检和换 ID，用独立路线核对定位偏差与重获，用新自由射线验证行人离开后障碍正确撤销，并检查是否新增了没有自由依据的空闲格。离线导出同时看接缝、人工区域、峰值内存、磁盘读写和总墙钟。只有在相同负载下改善目标指标、质量达到原要求的候选才值得改默认配置。
