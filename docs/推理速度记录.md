# 推理速度记录

本文按感知、导航、局部 VLM 和 Agent 保存最近可追溯的代表性记录。已保存结果来自不同版本与条件；当前代码尚未在相同现场条件下重新测速，不能据此推断最新性能或实机安全。

## 感知与导航

2026-11-09 轮椅端使用约 10 Hz 雷达、三帧 FP32 检测、18 米局部窗口和 10 Hz 地图目标频率；有地图、RViz 和目标请求，运行约 90 秒，安全为影子模式，轮椅未移动。901 张环境图按有效局部定位时间估算约 10 Hz；环境图处理 P50／P95 为 **11.74／13.96 ms**，源观察年龄为 **52.81／66.34 ms**。部分周期生成规划候选，另有规划不可用周期。数字来自此前的现场汇总；原始运行目录不在当前服务器，无法在此复核。

### 二楼导航优化回放

2026 年 11 月 22 日，在轮椅端 i7-12700 和 RTX 4060 Ti 上，用二楼地图和 11 月 19 日 16:42 的行人跟随 bag 做了六轮原速回放。旧版和新版各运行三轮，顺序为旧、新、旧、新、新、旧。两组均使用 18 m 局部窗口、7.5 Hz 地图目标频率和 TensorRT 跟随，运行参考规划、控制与独立安全检查。回放采用同步归档调度，未启动 RViz 或连接底盘。每轮均处理 478 帧扫描，发布 345 张地图，地图故障为零。

下表给出各版本三轮结果的范围，每轮单独计算 P50 和 P95。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 地图实际发布频率 | 7.49 Hz | 7.47～7.49 Hz |
| 进入原生搜索的请求，端点检查与代价图准备 P50 | 71.3～78.9 ms | 31.5～39.7 ms |
| 目标进入规划循环到首次取得对应参考路径 P95 | 419～521 ms | 426～483 ms |
| 源扫描到地图首次用于控制 P95 | 117～214 ms | 119～214 ms |
| 源扫描到地图首次用于独立安全几何检查 P95 | 178～224 ms | 176～243 ms |

**端点检查与代价图准备的耗时稳定缩短，整链时延仍有波动。** 按时间戳对齐六轮控制端都使用过的 310 个源扫描，各轮首次用图时的地图年龄中位数均约 110～111 ms。前 10 秒两版均有较大延迟，去掉这段后仍有一轮新版 P95 达 209 ms。逐轮统计、路径形状对照图和计时日志保存在车载机的 `outputs/navigation/realtime_optimization_20261122/`。

- **参考工作图。** 在 12 个二楼封存查询上做单核交错对照，新观察直连请求的总耗时中位数从 89.60 降到 58.44 ms，重复观察直连从 30.04 降到 12.82 ms。对另取的 16 个连续查询，新建工作图中位耗时为 19.89 ms，其中局部几何投影占 13.40 ms。隔离测得整图复制和逐格比较各约 0.60 ms，因此暂缓跨帧分块。
- **局部环境图。** 168 帧中有 40 帧窗口原点不动，跳过四个地面数组的搬移后，各帧地图层、导航支持和安全数据逐字节一致。地面支撑缓存仅命中 309 次非空查询中的 33 次，二维占据与未知掩码在相同原点下仅有 3 帧可复用。取前 48 帧测量，线性 CUDA 距离变换平均 0.218 ms，原实现为 0.104 ms，三维全量准备、应用与体素投影合计约 1.12 ms。因此沿用现有地面支撑计算、距离变换与全量体素更新。
- **原生搜索。** 在六个进入离散搜索的现场查询中，预计算八邻域边权后，各查询的冷搜索耗时中位数下降约 5%，输出路径一致。

## 局部 VLM

2026-11-16 使用 10 月 23 日 bag 的两组三帧 RGB／BEV，通过托管 `qwen3.8-flash` 和 JSON Schema 约束检查两字段 T2 输出；两次完整返回分别约 **1.54／1.43 秒**。另以移除可选人物的模拟输入检查观察点选择，完整返回约 **1.41 秒**。三次格式均有效，输出分别为 13、13、14 token。请求含新连接和图像上传，服务硬件未知；模拟输入不证明真实丢失时的行为，少量样本不能评价在线识别或延迟分布，也不能代表 DSPARK 的性能。预览为未随 Git 提供的实验产物 `outputs/decision/t2_two_field_preview/index.html`。

T1 和 T3 尚无当前接口的独立速度结果。历史三帧托管 API 开发对照中，两类完整返回中位数约 1.2 秒，使用 `qwen3.8-flash` 和三张 1280×576 PNG。当前 SGLang＋DSPARK 接口、模型和输入下的时延仍待测量。历史报告为未随 Git 提供的实验产物 `outputs/decision/hosted_tasks/wheelchair_20261102/report.md`。

## T2 本地身份匹配

2026-11-21 在开发服务器上以 RTX 3090、TensorRT FP32 原速回放 `follow1.bag` 前 29 秒。使用同一目标裁剪，将外层 Agent 的跟随图像改为按需生成后，T2 工作线程稳定阶段的墙钟耗时 P50／P95 从 154／214 毫秒降至 56／80 毫秒。控制线程尝试应用的结果从 69 个增至 99 个，源扫描到尝试应用的中位时延从 318 毫秒降至 219 毫秒。P95 从 417 毫秒升至 431 毫秒，超过 500 毫秒的结果从 3 个增至 5 个。按 RGB 和雷达源时间同时对齐的 62 帧上，中位时延也为 318 与 219 毫秒，P95 分别为 417 与 508 毫秒。一次较早的改后回放提前结束，具体原因没有保留下来。上述完整对照只衡量服务器回放，实际运动与轮椅端时延仍需测量。

2026-11-22 在轮椅端 RTX 4060 Ti、CUDA 12.9、TensorRT 10.13.3.9.post1 上，将 11 月 19 日 16:40 和 16:42 的二楼行人演示 bag 各原速完整回放两次。两种配置均运行地图定位、三维跟踪、参考规划和控制。环境图使用 18 米窗口和 7.5 Hz 目标频率。影子会话从当前唯一关联行人建立参考，未调用远程模型或连接底盘。表中的工作线程耗时为墙钟耗时，应用年龄为源扫描到控制线程接纳结果的测量时间差，均含首个结果。

| bag 起始时间 | 二维检测与身份匹配后端 | 接纳结果数 | T2 工作线程 P50 / P95（ms） | 应用年龄 P50 / P95（ms） |
| --- | --- | ---: | ---: | ---: |
| 16:40 | PyTorch YOLO FP16 + OpenCV CPU OSNet | 333 | 33.6 / 59.9 | 111.0 / 212.8 |
| 16:40 | TensorRT YOLO FP16 + TensorRT OSNet FP32 | 374 | 15.7 / 30.9 | 110.4 / 210.6 |
| 16:42 | PyTorch YOLO FP16 + OpenCV CPU OSNet | 323 | 25.7 / 31.4 | 109.3 / 115.3 |
| 16:42 | TensorRT YOLO FP16 + TensorRT OSNet FP32 | 313 | 15.8 / 31.5 | 111.1 / 211.4 |

为单独比较推理，从两份 bag 各取 8 张相同的 640×480 RGB。YOLO 的 640×640 网络输入经一次预热后，逐图检测并返回主机的中位耗时由 5.65 降至 3.96 ms。两种后端的 17 对检测框全部匹配，最小 IoU 为 0.987。对相同的 17 个人框逐个提取 OSNet 特征，含预处理和返回主机的中位耗时由 10.45 降至 1.51 ms，最小余弦相似度为 0.99999994。

双引擎缩短了两份 bag 的工作线程中位耗时。控制线程接纳结果还受扫描处理和控制调度影响。第二份 bag 按同一雷达与 RGB 时间戳配对的 309 个结果中，应用年龄 P95 仍由 115.3 升至 210.4 ms。两种配置各只回放一次，首次选人的图像也可能不同；这些数据未评估身份正确率、实车响应或长期时延。
