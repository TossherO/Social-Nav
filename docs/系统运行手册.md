# 系统运行手册

以下命令从仓库根目录执行。按本机的 `ENVIRONMENT.local.md` 选择解释器、GPU、数据和地图，输出使用新目录。首次拉取参见[车载机接入](开发指南.md#车载机接入)，现场待核对事项见[系统实机问题](系统实机问题.md)。

## 准备

先激活本机的模型运行环境，并用 `SOCIAL_NAV_PYTHON` 指定其中的解释器。系统 ROS 解释器由 `configs/runtime.yaml` 的 `input_python` 选择，ROS 环境脚本加载 Noetic。

```bash
export SOCIAL_NAV_PYTHON=/path/to/project/env/bin/python
export GPU_ID=0
source perception/scripts/ros1_env.sh
```

首次部署缺少车载构建产物时，先准备系统依赖和 ROS 工作区，再按目标机 CUDA 与编译器构建直接运行时。ROS 全量构建需要另外提供 `data/cache/perception/` 中的固定依赖缓存，准备脚本会从缓存解包。已有环境按缺失产物和源码变化选择相应构建。[ROS 构建依赖](perception/技术实现-建图与定位.md#运行环境与构建)

```bash
bash perception/scripts/build_ros1.sh all
SOCIAL_NAV_CUDA_ARCH=86 CUDACXX=/path/to/nvcc SOCIAL_NAV_CXX=/path/to/g++ \
  BUILD_JOBS=2 bash perception/scripts/build_runtime.sh
source perception/scripts/ros1_env.sh
```

命令中的 CUDA 架构和编译器路径按本机修改。交互预设用 `taskset` 设置 CPU 亲和性。若车载机的可用 CPU 不同，按该机的允许范围设置 `SOCIAL_NAV_COMMISSIONING_CPU_LIST`。[开发指南](开发指南.md#选择运行环境) · [车载性能预设](../navigation/commissioning/performance.env)

按实际启动的预设准备本车地图。每份预设中的 `map` 指向 ROLL 三维定位图，`static_map` 指向环境和规划使用的静态地图，`initial_pose_hint` 提供选点时的高度与姿态提示。显式配置 `coverage` 时使用与该定位图相符的关联区域。Agent 还读取对应静态地图的 `catalog`。这些现场资产位于 Git 忽略的目录，应保留本车已有的配套文件，或把匹配的资产放在相应预设指定的位置。

| 用途 | 预设 |
|---|---|
| 部署自检与直接执行 | [interactive.yaml](../navigation/commissioning/interactive.yaml) |
| 普通无底盘观察 | [interactive_observation.yaml](../navigation/commissioning/interactive_observation.yaml) |
| 二楼 Agent 人工驾驶观察和单楼层回放 | [interactive_agent.yaml](../navigation/commissioning/interactive_agent.yaml) |
| 一楼 Agent 人工驾驶观察和单楼层回放 | [interactive_agent_floor1.yaml](../navigation/commissioning/interactive_agent_floor1.yaml) |

基础感知导航还需要对应的三维检测权重及兼容的 CUDA 扩展。T2 需要额外的二维人物检测权重、可用相机标定和所选跟随后端。Agent 使用托管 API，凭证在车载机单独准备。[检测与跟踪推理](perception/技术实现-检测与跟踪推理.md) · [Agent 服务配置](decision/技术实现-Agent长程导航.md#服务配置与思考模式) · [T2 后端与权重](#启用持续跟随)

## 日常运行与回看

### 从bag运行感知导航

有图定位使用相互对应的三维定位图、起点、可信区域和静态环境图：

```bash
bash scripts/run.sh --bag /path/to/input.bag --mode localization \
  --map /path/to/localization_map --pose-file /path/to/initial_pose.json \
  --coverage /path/to/coverage.yaml --static-map /path/to/static_map \
  --output outputs/perception/new_run --gpu "$GPU_ID"
```

省略 `--coverage` 时按所选地图自动生成全图关联范围；不使用静态先验时省略 `--static-map`。无图局部定位使用 `--mode odometry`。离线有图定位在匹配积压时等待后端，实际处理时间可能超过录制时长。`summary.json` 和 `run.json` 分别记录运行结果与输入配置。停止时首次 `Ctrl+C` 请求排空并保存。

### 使用在线传感器

先启动真实设备，再运行观察：

```bash
bash perception/capture/start_sensors.sh
bash scripts/run.sh --live --mode odometry --duration 60 \
  --output outputs/perception/new_live --gpu "$GPU_ID"
```

bag 模拟 live 时必须提供 `/clock`；真实设备使用真实 ROS 时间，不叠加另一份回放。

### 选择传感器时钟会话

默认使用传感器原始时间，不在启动时自动估计时差。显式补偿及安装标定应与本次设备和数据一致，见[建图与定位](perception/技术实现-建图与定位.md)。

### 按录制路线生成分段目标

回放路线仅用于对应 bag 的影子测试；按[任务与路线](navigation/技术实现-任务与路线.md#录制行程的分段目标回放)选择路线及地图，不代表轮椅执行。

### 结果回看

检查 `summary.json`、`reference.jsonl`、控制与安全日志；可视化命令及数据来源见[接口约定](接口约定.md)和[推理速度记录](推理速度记录.md)。

## 实机部署自检

```bash
bash scripts/interactive.sh preflight
bash scripts/interactive.sh execute --check
```

本车观察、执行和档案检查都从所选交互预设读取 `motion_config` 和 `motion_profile`。第一条输出各项检查的状态和失败细节，涵盖执行预设的地图配套、三维检测资源、CUDA、原生库、ROS 与 RViz 插件。第二条检查执行所需的车辆档案。两条命令均不连接底盘，实际停车须现场确认。检查其他楼层的地图和软件时，先加载 ROS 环境，再用选定的本机 Python 运行 `-B -m runtime.preflight --config 预设路径`。

## RViz交互测试

### bag 暂停与选点

```bash
roscore
# 另一终端
bash scripts/interactive.sh --bag /path/to/localization.bag --pause-at 8 \
  --gpu "$GPU_ID" --output outputs/navigation/new_bag_session
```

人工使用 `Ground Pose Estimate` 选择雷达起点，使用 `Ground Nav Goal` 选择车体目标及朝向；已保存起点只能用于相匹配的 bag、地图和偏移。终端 `p` 暂停、`r` 继续、`s` 取消、`q` 退出；当前不能倒退，需重启选择较早位置。冻结曲线只是预览，不向底盘发送指令。

### 现场观察与执行

```bash
bash perception/capture/start_sensors.sh
bash scripts/interactive.sh observe
```

观察模式不连接底盘。选择起点后，可在 RViz 的 `Social-Nav session` 面板按按钮或使用 W/S 前后、A/D 左右平移，Q/E 旋转；平移按起点朝向计算，每次 0.05 米，旋转每次 5°。检查点云与地图对齐后，点击顶部工具栏的 `Confirm Initial Pose` 确认起点。该微调仅适用于实机初始化前的预览，bag 选点仍立即初始化。

执行前先在观察会话中确认实时扫描与本车地图对齐，用当前目标查看参考路径，并核对会话记录中的地图关联状态。若定位或预览未建立，先根据本次会话的 `runtime.log` 和 `run/reference.jsonl` 查原因。

启动检查会验证面板插件声明和本机库的接口标识。若提示插件缺失、过旧或无法加载，运行 `bash perception/scripts/build_ros1.sh visualization` 重新构建，再重新启动观察或执行会话。

停止观察会话后，如已有现场授权与准备，可改用执行预设。

```bash
bash scripts/interactive.sh execute --execute
```

执行预设读取本车档案，使用面板“轮椅使能”进行人工使能。“取消 / 退出使能”和“退出会话”沿用原会话命令；手柄接管、急停、命令超时和独立安全仍生效。终端 `c`、`a`、`s`、`q` 仍可用。目标接收、规划曲线与定位估计不等于车辆实际到达或停车。

### 显示与提交目标

参考路径显示完整 XY 路线，优先使用局部及静态地图的地面高度；缺失处用插值或回退高度显示，并在状态中标注近似值。这些高度仅用于显示，不代表实测地面或可通行。DWA 轨迹无高度时仍可能断开。目标位置是箭头起点而非箭头尖端。没有有效地图关联时，不发布虚构的地图位姿。

### 底盘受控检查

按 `bash scripts/interactive.sh execute --help` 和[本车档案](../configs/wheelchair_vehicle.yaml)使用。改变协议或排查底盘时保留串口独占、人工接管、急停和看门狗；历史对照见[现场归档](archive/感知导航现场历史.md)。

### 固件断发停车检查

固件断发停车尚未完成现场确认，按[系统实机问题](系统实机问题.md)记录实际现象；不得把软件超时或影子停车当作固件验收。

## Agent 长程任务

人工驾驶调试时，先启动传感器，再运行不连接底盘的观察会话并在 RViz 确认初始位姿：

```bash
bash scripts/interactive.sh observe --agent-observations --floor floor2
```

启用 `--agent-observations` 时，`--floor floor2` 选择[二楼 Agent 人工测试配置](../navigation/commissioning/interactive_agent.yaml)，`--floor floor1` 选择[一楼配置](../navigation/commissioning/interactive_agent_floor1.yaml)；不指定楼层时使用二楼。两份配置分别指定定位图、静态图和高度初值，该入口不连接底盘。地图缺少单独关联区域时自动采用全图关联范围。观察程序启动后，在 RViz 确认实时扫描与地图基本对齐。

在另一终端激活同一模型环境并设置相同的 `SOCIAL_NAV_PYTHON`。Agent 窗口需要 PyQt5 和桌面会话，任务调用需要[托管 API 的本机连接配置](decision/技术实现-Agent长程导航.md#服务配置与思考模式)。启动窗口后，选择观察终端打印的本次会话目录及与当前地图匹配的语义标注。

```bash
"$SOCIAL_NAV_PYTHON" -B -m decision.agent.manual_ui --floor floor2
```

窗口的楼层预设填写配置指定的语义标注路径；如果该地图尚无标注，界面会提示先创建。更换地图后，旧地图标注不能直接沿用。切换预设会清除之前选择的观察会话，须重新选择同一楼层当前运行的会话目录。输入任务并点击“开始新任务”。对话区的“当前请求”按最近一次实际模型请求的顺序显示消息，并列出消息数量和图片数量；模型刚产生的回复可能尚未进入该请求。“历史记录”按消息首次出现的时间显示请求、模型输出和工具结果，消息状态说明其是否出现在最近请求中，或仍等待进入下一次请求。双击消息或图片只查看该消息的内容与图片；“查看整轮请求”查看最近请求的全部内容，历史中的请求行也可双击查看整轮。图像是请求当时的观察，不代表当前画面。“查看工具”列出工具描述和参数，并标记最近一次请求提供的工具。

开始任务前，可在会话设置的“任务登记思考强度”选择“无”、`low` 或 `medium`，默认 `low`。该选择仅用于任务分解与登记；登记后的目标选取和任务监控仍关闭思考。运行中的任务不能更改此设置，需要在开始新任务前选择。思考可能增加响应时间，`medium` 的模型输出上限也高于 `low`。

重复测试已有任务时，可在会话设置中点击“选择历史任务”，选择原会话的 `session.sqlite`，查看原指令、澄清和完整登记要求，确认后点击“开始新任务”。程序在新会话中从第一项重新执行，不重复调用模型登记；任务登记思考强度在此模式下不生效。历史目标、路线、执行进度和到达证据不会带入。新会话仍需当前观察和定位，并核对地图、标注和起始楼层；跨楼层任务须勾选跨楼层选项，较早的跨楼层记录若缺少某一楼层的地图来源则无法复用。可点击“取消复用”恢复输入新任务。

任务启动或打开历史会话后，会话设置自动收起；需要更换观察目录或标注时可再次展开。拖动左侧任务列表、任务监控与目标示意图之间的分隔条，可以调整各区域的高度；拖动对话区与运行事件区之间的分隔条，可调整两者的高度。任务监控内容更新时保留当前滚动位置，长内容可滚动查看。

界面隐藏或缩略用于校验的长标识；原始会话记录保留完整内容。模型使用短引用指代地图或观察，程序会在调用工具前核对并还原这些引用。

人工驾驶状态区固定高度，内容较长时可滚动查看。目标示意图可双击或通过“放大查看目标示意图”打开；在消息详情中，选择图片后可双击图片或点击“放大查看选中图片”。独立图片窗口支持滚轮缩放、左键拖动，以及适应窗口和原始大小显示。

“子任务与要求”列出已登记的任务，选择一项可在下方查看完整要求，包括目标和用户指定条件。“任务监控”显示当前楼层、目标距离、停稳持续时间、必要的朝向误差、参考路径状态，以及最近一次复核触发和 Agent 判断；距离和停稳均来自定位估计。需要提前复核时可点击“立即复核”，这不会确认到达或控制手柄。运行事件区显示监控触发、到达证据等待、参考路径状态和上下文裁剪等事件，可双击查看详情；监控触发也会通知 Agent。历史会话通过“打开历史会话”只读查看，不会自动恢复执行。窗口创建新的输出目录并管理人工 Agent 进程，关闭窗口会结束该任务进程。窗口的路线进度来自定位估计；发送按钮操作后等待 Agent 接收或拒绝，操作超时不会自动重试。

普通任务到达后，Agent 根据定位、停稳及任务要求自行决定下一步。如果指令要求“到电梯口后等我通知再乘梯”，可在“子任务与要求”核对“完成后等待口令”。到达后状态区显示对应原话，点击“继续”才进入乘梯阶段。看到具体澄清问题时点击“发送答复”。若显示“模型未提交执行动作”，说明执行模型连续两次只返回文字，任务已请求暂停，可在确认暂停后点击“恢复”。

条件式持续复核会显示所用区域、轮椅在区域内外或定位不可用，以及等待观察、等待复核和模型判断中的状态。跟随任务同时显示 T2 状态。开始测试后，在“子任务与要求”核对任务登记的完成区域；条件式监控负责触发判断，只有登记了完成区域要求时，提交完成才会再次核对轮椅是否仍在该区域。连续复核会增加模型调用，人工窗口默认每次任务最多 512 次请求。

开始任务前可勾选“任务执行时自动录制传感器 bag”。任务登记完成后，程序连接该观察会话使用的 ROS master，检查传感器并等待录包文件实际写入数据，再让 Agent 开始执行阶段的决策。窗口沿用代码中为本车设置的默认采集目录。若该路径在当前机器不可写，可用下文的命令行入口指定本机输出根目录。每次录制在 `navigation_时间/` 下保存 `navigation.bag`、`capture.json`、录制日志及 SHA256。包包含雷达、IMU、相机图像、相机内参和静态 TF，Agent 的任务、对话与运行事件留在独立的 Agent 会话目录。暂停、等待用户以及人工驾驶的跨楼层过程都包含在同一任务的录制中。录制从登记结束后开始。

窗口的自动录包状态栏显示准备、录制、关闭校验、保存或失败及文件路径。正常结束、取消任务或关闭窗口时会请求停止；Agent 进程异常退出时，录包进程也会自动停止并完成收尾。bag 关闭后仍需校验话题、索引并计算完整 SHA256，校验期间显示“正在关闭与校验”。启动前检查失败会阻止执行阶段并提示原因；处理原因后需取消并重新开始任务，或在新任务中取消勾选录包。运行中录包失败会显示警告，已有人工驾驶任务继续，录制不自动重试。成功状态只说明索引、必要话题数量与完整文件摘要已检查，不代表逐消息数据质量已验收。等待当前包保存完成后再开启下一份自动录制，避免与现有采集程序争用独占锁。

命令行人工模式可使用 `--record-bag` 启用相同功能，使用 `--bag-output-root` 指定输出根目录。若观察会话在更新前启动，需重启观察程序，使其向 Agent 提供所连接的 ROS master 地址。bag 影子回放不支持这项自动录制。

人工驾驶时，如当前子任务无法完成，可点击“跳过当前子任务”并确认。程序取消当前参考目标，待取消确认后将该项标为“已跳过”，并继续后续子任务；如果没有后续子任务，任务以“部分完成”结束。跳过不会记录为到达或任务成功，也不会控制手柄或让轮椅停车。乘梯阶段不能跳过，自动执行模式不提供此操作。

如已单独取得历史离线演示，可以打开其会话数据库：

```bash
"$SOCIAL_NAV_PYTHON" -B -m decision.agent.manual_ui --session /path/to/session.sqlite
```

演示包括二楼标注地图、RGB、全局轨迹图与局部地图，均来自当时发送给模型的历史冻结观察，不是当前实时画面，也不代表实机任务验收。

也可以不使用窗口，直接在终端中运行人工 Agent。使用本次观察会话输出目录中的 `run/commands.sock` 和匹配的语义标注；输出目录必须是新目录：

```bash
"$SOCIAL_NAV_PYTHON" -B -m decision.agent manual --runtime-socket /path/to/observation/run/commands.sock \
  --catalog /path/to/catalog.json --instruction '绕圆形区域一圈' \
  --interactive --duration 1200 --output outputs/decision/agent/new_manual_session
```

命令行复用历史登记时，将 `--instruction '…'` 换成 `--reuse-session /path/to/old/session.sqlite`；跨楼层任务同时传入 `--cross-floor`。输出仍须使用新的目录。

Agent 的目标和路线是人工驾驶建议，不会发送底盘指令。人工模式会在无底盘输出的观察会话中请求当前目标的参考路径预览；多点任务预览当前待经过的点。窗口和终端显示预览是否生成及失败原因，RViz 中白色参考线为规划器结果；目标标记和途经点之间的蓝色直线表示经过顺序，不是规划结果。单点目标的洋红色箭头表示 Agent 选定的朝向，多点路线在终点提供朝向时也显示箭头；是否需要对准以任务要求和窗口状态为准。预览缺失时不表示路径可通行。两种显示都不能保证现场安全通行，规划失败时请结合现场情况决定如何继续。参考线缺失的地面高度会用显示近似值补全。

Agent 标记高度优先使用地图地面高度；无对应高度时使用地图地面高度中位数，仅用于显示，并提示近似高度的点。地图完全缺少地面高度时，该点不显示。操作原车手柄到达目标并停稳后，人工模式根据新鲜地图定位、位置容差、必要的朝向容差和连续停稳估计自动检查到达。位置容差为 0.20 米，连续停稳时间及其他阈值使用导航配置；这些条件必须在新鲜测量中持续成立，不能仅凭规划成功推进。到达证据失效后，满足条件时会重新生成；也可以使用窗口的“人工确认（备用）”或终端 `arrived` 辅助确认同一目标，仍须通过定位和停稳检查。对话中回复已到达只是补充说明，不会单独产生到达证据。多点路线依次记录实际经过的途经点，中间点可连续经过；终点停稳后由 Agent 结合原任务、轨迹和当前观察判断完成情况。目标 PNG、事件和任务证据保存在该会话目录。`pause`、`resume`、`cancel`、`answer 补充说明` 和 `replace 新指令` 用于管理 Agent 任务；取消任务或关闭窗口不会控制原车手柄或停车。

人工驾驶窗口勾选“跨楼层任务”后，选择与当前地图相符的观察会话。开始前确认两层配置指向现场地图与标注，ROS 相机和原始雷达话题独立于定位进程。进入已登记的乘梯子任务后，程序自动关闭来源楼层的只读定位并启动独立传感器观察，不要求当前停稳或来源地图关联有效；启用自动录包时须先等待录包就绪。由操作者驾驶轮椅进出电梯并操作电梯。目标楼层有标准起点时，将轮椅驾驶至该位置、调整至参考朝向并停稳；Agent 默认每 5 秒对照当前 RGB、局部雷达图与标准起点的历史参考图，判断是否到达。实时画面和本机保存的参考图会发送给所配置的 Agent 模型服务。窗口可查看乘梯及目标楼层定位期间的实际请求、图片和模型判断，每个阶段结束后清除该阶段的临时内容；观察故障也会显示在窗口中。

外层 Agent 模型服务遇到连接超时等临时故障时，界面会显示提示并保留当前阶段。首次等待 5 秒，连续失败时等待时间逐次加倍，本地等待最多 60 秒。如果服务端通过 `Retry-After` 要求等待更久，按服务端时间执行。乘梯监控在等待结束后还须取得新观察。收到正常响应后，下一次故障从 5 秒开始计算。认证错误、模型响应不符合协议或达到请求上限时，流程暂停等待处理。

一楼的标准起点取自采集参考图时的雷达地图位姿。首次测试跨楼层任务前，核对一楼地图与标准起点记录，并按 `reference_observation` 配置准备本机参考文件 `reference.json`、`rgb.jpg` 和 `lidar.png`。程序会检查地图身份和图像摘要。Agent 判断轮椅已到标准起点后，程序取得新的出梯扫描，用配置的完整雷达位姿自动尝试一次定位。若提示缺少新扫描，先检查独立传感器流。[标准起点配置](../decision/agent/configs/elevator_standard_starts.json)

标准初值启动失败，或尝试开始后 30 秒内未取得有效的一楼地图关联时，原任务保留在乘梯阶段。程序自动打开一楼 RViz 人工选点窗口。保持轮椅停稳，用 `Ground Pose Estimate` 选择雷达的位置和朝向，对照当前雷达点云与地图调整，再点击 `Confirm Initial Pose`。选点和预览不占配准时间，确认后每次配准最多等待 30 秒。若仍未配准，程序再次打开人工选点。若选点窗口意外关闭或启动失败，可在 Agent 窗口查看原因，点击“重开选点窗口”。目标地图关联有效后，Agent 自动收到定位证据并继续原任务。

目标楼层没有标准起点时，由 Agent 根据出梯后的扫描和目标地图选择初值。如果配准失败或超时，Agent 可根据新的扫描及上次尝试的叠图重新选点。

人工路线和观察阶段已通过合成数据检查，连续单点及一轮绕行组合任务已有人工驾驶现场记录；其他任务及完整跨楼层流程仍需验证。模型调用会向所配置的服务发送任务和当前需要的地图、RGB 等输入，应在现场测试前确认数据发送范围。

观察会话或 RViz 异常退出时，参考路径和地图定位不再更新；人工驾驶者应使用原车手柄停稳，再查看该观察会话的 `runtime.log` 和 Agent 会话事件。关闭观察程序不会控制手柄或使轮椅停车。若模型只回复文字，界面会等待用户；查看回复和任务状态后可补充说明，但不能把文字视作子任务完成的证明。

实机自动执行使用不同入口，需明确打开 Agent 通道：

```bash
bash scripts/interactive.sh execute --execute \
  --agent-observations --agent-follow-candidates --agent-execution
# 另一终端，使用本次会话输出的 socket 和匹配当前地图的语义目录
"$SOCIAL_NAV_PYTHON" -B -m decision.agent execute --runtime-socket /path/to/run/commands.sock \
  --catalog /path/to/catalog.json --instruction '导航到门口' \
  --interactive --output outputs/decision/agent/new_session
```

确认地图定位并人工使能后才可运动。可将指令改为描述目标人物和跟随终止条件。Agent 的 `cancel` 取消任务，交互终端 `s` 撤销目标和使能。Agent 在收到目标、停稳和当前观察证据后提交完成决定。持续跟随尚未通过实机闭环验证。T1 仍待接入。

### 启用持续跟随

人工驾驶观察时使用 `observe --agent-observations --agent-follow-candidates`。驾驶者继续操作原车手柄，动态参考只供显示。首次选人使用共用的 YOLO 二维人物检测，需要[检测配置指定的权重和图像依赖](perception/技术实现-检测与跟踪推理.md)。持续跟随默认使用 DSPARK，请按[远程服务启停与访问](decision/技术实现-VLM局部决策.md#远程服务启停与访问默认)让车载机连通公共配置指定的地址和模型。可用 `--t2-backend hosted` 选用 Agent 托管 API。轮椅预设为两种远程后端默认发送质量 80 的 JPEG，可用 `--t2-jpeg-quality` 调节质量，或用 `--t2-image-format png` 发送 PNG。变更后端或图像格式需要重启观察程序。

本地 OSNet 后端从 Agent 首次选中的人物裁剪建立参考，之后用当前 RGB 和同源二维、三维关联持续核对身份。运行需要可用的相机标定。`--t2-reid-weights` 指向 `.onnx` 时使用 OpenCV CPU，指向 `.engine` 时使用 TensorRT CUDA。

可以把已导出的 ONNX 复制到轮椅的 `models/follow_reid/`，并用 `sha256sum` 对照转移前的文件摘要。仅从 Git 准备时，先通过导出工具的帮助获取固定的上游源码和权重地址，再在具备 PyTorch、ONNX 和 OpenCV 的环境中导出。导出工具检查两份上游材料的摘要，并比较 PyTorch 和 OpenCV 的特征输出。

```bash
python -B -m decision.osnet.export_reid --help
python -B -m decision.osnet.export_reid /path/to/osnet.py /path/to/checkpoint.pth \
  models/follow_reid/osnet_x0_5_msmt17.onnx
```

选择 GPU 推理时，按轮椅本机环境记录激活运行时所用的 Python、TensorRT 和 CUDA 环境，并让运行时所用的 GPU 可见，再从这份 ONNX 构建 FP32 引擎。若已知原 ONNX 的 SHA256，可用 `--onnx-sha256` 在构建前核对。引擎和生成的 `.engine.json` 须留在同一目录。更换 GPU 型号或 TensorRT 版本后，从 ONNX 重新构建到新路径，避免覆盖已有引擎。

```bash
python -B -m decision.osnet.build_reid_engine \
  models/follow_reid/osnet_x0_5_msmt17.onnx models/follow_reid/osnet_x0_5_msmt17.engine
bash scripts/interactive.sh observe --agent-observations --agent-follow-candidates \
  --t2-backend reid --t2-reid-weights models/follow_reid/osnet_x0_5_msmt17.engine
```

引擎无法加载时，跟随会报告失败。检查引擎、同名 JSON 和本机 GPU 环境，或改用 `.onnx` 路径重启观察程序以启用 CPU 后端。首次跟随得到局部结果后，在 `run/reference.jsonl` 的 `follow_t2_result` 事件中查看 `reid_model`，其中记录实际后端、设备、模型路径、模型及原始 ONNX 摘要。

也可以在本机的 `configs/t2_backend.local.json` 中设置 `{"backend":"reid","reid_weights":"models/follow_reid/osnet_x0_5_msmt17.engine"}`，命令行设置优先。跨楼层交接沿用当前后端和权重路径。`reid` 的持续 T2 在本机处理，外层 Agent 选择目标和复核任务时仍使用自己的托管 API。模型输入和后端时效见[T2 行人跟随](decision/技术实现-T2行人跟随.md)。

桌边停靠在 `observe` 或已授权的 `execute` 入口使用 `--agent-observations --agent-seating`，需要局部 DSPARK 服务、可用相机标定和当前扫描。请先在可看清目标桌沿的位置停稳。首次跨楼层与局部任务组合仍需现场验证。

排查 T2 时延或地图关联中断时，可在 `observe` 命令中加 `--trace-timing`。结束本次观察后，输入进程的匹配事件在 `run/timing_input.jsonl`，主进程的感知和控制事件在 `run/timing.jsonl`。两个文件各有一份 `.summary.json` 记录写入和丢弃条数。跨楼层自动启动的目标楼层进程有独立的 `command.json`，当前不会继承该开关。

人工驾驶观察可在 DSPARK 或托管后端使用 `--t2-raw-rgb` 做对照。Agent 首次选人仍使用 YOLO。持续 T2 使用原始 RGB 和独立俯视图，由模型判断人物与三维轨迹的对应。该实验缺少跟随结束所需的当前二维关联证据，仅用于非执行观察。切换至 `reid` 前须去掉 `--t2-raw-rgb` 并启动新会话。

### bag 回放调试 T2 跟随

本机可使用与实机人工调试相同的 Agent 窗口，结合 RViz 对已有导航 bag 进行非执行回放。入口创建独立 ROS master，默认读取二楼定位地图、静态地图及语义标注，并启用人物检测与 T2 跟随决策。脚本默认使用托管 API，请求包含 bag 中的人物图像和相关观察，图像默认采用质量 70 的 JPEG。`--t2-backend dspark` 选择远程 DSPARK，默认使用 PNG。两种 VLM 后端均可用 `--t2-image-format jpeg --t2-jpeg-quality 80` 选择质量 80 的 JPEG，或用 `--t2-image-format png` 选择 PNG。下面的命令显式选择本地 T2 后端，权重准备见[启用持续跟随](#启用持续跟随)。

回放使用 `SOCIAL_NAV_PYTHON` 或已准备的当前环境。车载机若已有 `outputs/runtime/environment/activate.sh`，脚本会加载该本机环境；显式指定的解释器优先。回放需要 Noetic、原生库、RViz 插件及对应楼层资产。

```bash
cd /path/to/Social-Nav
bash scripts/t2_bag_replay.sh \
  --bag /path/to/navigation.bag --t2-backend reid \
  --t2-reid-weights models/follow_reid/osnet_x0_5_msmt17.engine
```

RViz 出现后，用 `Ground Pose Estimate` 选择 **bag 录制起始时**的雷达位置与车头方向；选点后立即启动定位。定位就绪后，在 Agent 窗口输入包含目标外观的跟随任务，例如“跟随前方穿深蓝色上衣的人”，再点击“开始新任务”。Agent 窗口显示任务、对话及 T2 最近状态，RViz 显示回放中的感知和规划。会话终端输入 `p` 暂停、`r` 继续、`q` 退出。暂停期间没有新观测，正在执行的跟随任务可能因状态过期而取消；播放结束后需重新启动才能重放，不能用 `r` 从头播放。

默认 1 倍速，以便比较时间相关行为。`--rate 0.5` 可放慢播放，`--start 秒` 可从指定录制偏移开始。播放速度变化会影响结果返回时的观察年龄，实时性数据应注明播放倍率。使用一楼地图加 `--floor floor1`。ROS 端口冲突时可用 `--ros-port` 指定其他端口。

若要跳过 RViz 选点，可以用 `pick_start.sh` 查看首帧扫描与 RGB，在对应三维地图中保存初值，再通过 `--pose-file` 加载。初值文件与 bag、地图及 `--start` 偏移绑定。回放开始后仍需核对地图关联和扫描对齐。本机两份演示的路径和已准备初值见被 Git 忽略的本机环境记录。手动选点时可用 `--initial-z 米` 指定雷达高度初猜。

对于已经完成登记、第一项为跟随的任务，可以预先准备该 bag 的初值文件和历史 Agent `session.sqlite`，随后自动启动跟随：

```bash
bash scripts/t2_bag_replay.sh --bag /path/to/navigation.bag \
  --pose-file /path/to/bag_initial_pose.json \
  --reuse-session /path/to/registered_task/session.sqlite --auto-follow
```

程序启动时读取已登记任务并核对楼层、地图与标注。定位和当前地图观察就绪后，Agent 根据本次带编号的观察确认人物和参考图，再启动第一项跟随。外层模型参与选人，已登记的任务分解直接沿用。初值仍须经过本次地图关联。VLM 后端需要约 1 秒的有效三帧观察才会发起请求，失败时等待人工处理。`reid` 使用最新一帧，身份需要两次连续确认。没有初值文件时可在 RViz 手动选点后使用自动跟随。历史任务的第一项不是跟随，或地图及标注发生变化时，自动启动会拒绝并给出原因。

已知目标是单人演示中的行人时，可以在上述命令中加 `--auto-follow-single-person`。定位就绪后，如果当前 RGB 图像只检测到一人，而且此人与已确认的三维轨迹匹配，程序就用本帧裁剪建立参考并启动跟随。画面没有候选，或唯一候选还没有匹配轨迹时，程序等待新观察。一旦同一帧检测到多人，即使只有一人匹配轨迹，也会退出快捷启动，由外层 Agent 按原任务指令选人。

RViz 的目标点表示 T2 当前期望位置。参考线表示规划器当前采用的路径，可能通往通过车体检查的替代终点。局部轨迹在参考和当前观测足以通过 DWA 检查后才出现。VLM 选择原地转向时需要停稳证据。使用 OSNet 时，检查前往最后观测位置期间目标和修订号是否保持一致，并区分路径预览、录包中的轮椅运动和实际到达反馈。

终端打印的回放目录下，`interactive/run/reference.jsonl` 记录 T2 结果、等待中的跟随点、搜索拒绝和规划结果。`interactive/run/control.jsonl` 用于核对 DWA 是否生成局部轨迹及其拒绝原因。`interactive/run/t2_requests/` 保存 VLM 后端的实际请求、结果及人物图像，或本地后端的 `*.reid_observation.json`，其中包含观察来源、匹配评分和搜索选择。按原始数据保护这些记录，通过 `recording_summary.json` 的 `dropped` 和 `error` 检查写入是否完整。外层 Agent 的工具调用和任务状态可在 `outputs/decision/agent/replay_ui_*` 的 `session.sqlite` 查看。

回放位姿来自原始录制，生成的轨迹和速度属于影子建议。真实跟随、到达和制动由实机测试验证。当前影子回放支持单楼层观察。

只读状态与地图目录：

```bash
python -B -m decision.agent --help
python -B -m decision.agent status --session /path/to/session.sqlite
python -B -m decision.agent catalog --catalog /path/to/catalog.json
python -B -m decision.agent.map_annotation --static-map /path/to/static_map \
  --floor-id floor2 --vehicle-profile configs/wheelchair_vehicle.yaml --out /path/to/new_catalog.json
```

## 可选图像与决策输入

`--agent-observations` 提供与场景同期的 RGB。`--agent-follow-candidates` 启用 T2 所需的人物框和三维关联，启动跟随后按所选后端处理观察。`--agent-seating` 保留与当前 RGB 对应的扫描，在 Agent 指定桌沿后发送 T3 请求。`--record-decision-inputs` 可单独记录局部 VLM 的三帧输入。服务与输入要求见[VLM 局部决策](decision/技术实现-VLM局部决策.md)。


独立离线建图默认使用稳健回环，并假设采集的是地面大致水平的单层环境，随后自动做整体地面校正和关键帧高度软约束。最终定位图位于 `new_mapping/map`；原始建图保存在 `new_mapping/raw`，校正中间结果位于 `levelled` 和 `optimized`。短片段、地面支持不足或留出检查不通过时，整个流程报错并保留已完成阶段；如需原始算法，可在建图命令中加 `--pipeline raw`。该选项也用于与现有地图配准的局部更新。直接运行时的 `mapping` 模式不自动执行这些离线后处理。

静态导出使用具备 ROS 环境的系统 Python；`export --run` 默认使用同源封存扫描估计地面。没有完整扫描封存时，可明确选择 `--ground-method map_endpoints`；从定位地图直接导出和多次采集融合保留原有方式。定位图和静态图不可互换。建图完成不证明几何正确，应检查轨迹、墙面及高度一致性。地图分辨率与生成机制见[环境地图](perception/技术实现-环境地图与场景表示.md)。

排查高度错层时，可在建图时加 `--trace-roll`，再用 `python -m perception.mapping_localization.height_review --map /path/to/map --out /path/to/review.json` 查看重访统计。默认流程需要构建支持稳健回环的离线 ROLL 库，也可用 `--roll-library /path/to/library.so` 指定其他兼容库。结果应检查高度、墙面、占据和未知区域后再决定是否使用，不能直接视为实机验收。

也可对已有原始建图单独生成高度校正候选。以下命令都要求输出目录不存在；派生运行通过符号链接只读引用原扫描日志，移动或打包时需要保留该来源。`level_map` 可省略 `--static-map`，直接从该运行的同源封存扫描提取地面。

```bash
"$ROS_PYTHON" -B -m perception.mapping_localization.level_map \
  --run /path/to/mapping_run --static-map /path/to/tracked_scan_static \
  --out outputs/perception/levelled_candidate
"$ROS_PYTHON" -B -m perception.mapping_localization.ground_refine \
  --run outputs/perception/levelled_candidate --out outputs/perception/ground_candidate
"$ROS_PYTHON" -B -m perception.environment export \
  --run outputs/perception/ground_candidate --ground-method tracked_scans \
  --out outputs/perception/ground_candidate_static --resolution 0.1 --export-pgm
```

整体校正后的地图不自动满足定位对重力方向的要求；地面软约束也可能扭曲真实坡道或墙面。使用前须检查对应的定位地图和静态地图，旧地图的人工修改及标注不能直接视为适用。两种修正的假设和留出检查范围见[建图与定位](perception/技术实现-建图与定位.md)。

若同一环境有多次保留了封存扫描的建图运行，可将它们融合到同一张最终定位地图：

```bash
bash perception/scripts/build_static_multi.sh \
  --map /path/to/final_localization_map \
  --evidence-run /path/to/first_mapping_run \
  --evidence-run /path/to/second_mapping_run \
  --out outputs/perception/multi_survey_static --gpu 0
```

每个 `--evidence-run` 对应一次完整建图运行，可以继续添加。脚本按传感器观测时间排序，依次要求为各 bag 在最终地图上选择初始位姿，再沿用各次建图记录中的传感器外参及时间参数重新定位。随后自动融合扫描并保存至输出目录的 `static_map/`。原始 bag、运行记录和扫描封存均须可用，时间段重叠或来源不一致时停止。

如果最终地图由这些历史地图逐次更新而来，可加 `--auto-initial-poses`。脚本会检查更新链和保留的旧关键帧位姿，复用各次人工选点或原始建图初值作为配准初猜；它们不代表配准已经成功。自动或人工初值都须经过有图定位和质量检查。若已有各 bag 在最终地图上的定位运行，也可用 `python -B -m perception.environment export` 重复传入成对的 `--evidence-run` 和 `--reference-run`，按对应顺序指定。

融合按采集时间由旧到新处理。一次采集形成有效占据或满足支持条件的空闲时覆盖更早的结论，未观测或无法分类的格子保留旧结果；这依赖各次传感器时间可比较，不保证检测出所有动态变化。检查各次配准和生成地图后再决定是否启用；历史人工修改和 Agent 标注不会自动迁移。

### 用局部 bag 生成三维地图更新候选

先让新 bag 从旧地图覆盖区域开始采集，并保留该 bag 的完整雷达和 IMU。在有桌面的终端运行：

```bash
bash perception/scripts/update_map.sh --bag /path/to/local.bag
```

脚本默认读取 `navigation/commissioning/interactive.yaml` 中的定位地图和关联区域，启动前校验它们是否匹配。弹出选点窗口后，根据地图、雷达首帧和可用的 RGB 对照选择 bag 首帧的雷达位置及朝向，核对预览并保存。关闭窗口而不保存会停止处理。保存后脚本自动完成整个 bag 的局部建图、旧图定位和候选生成，不连接底盘。

可用 `--map /path/to/old_map` 指定其他地图，未同时指定 `--coverage` 时自动按该地图的点云范围构建关联区域；需要限制范围时用 `--coverage /path/to/coverage.yaml` 指定对应地图的区域。用 `--gpu 0` 指定 GPU。默认在 `outputs/perception/` 创建带时间的目录，也可用 `--out` 指定该目录下或 `/tmp/` 下尚不存在的目录。步骤失败会停止并保留已生成的中间结果；修正问题后使用新输出目录重试。

运行目录的 `initial_pose.json`、`local_mapping/` 和 `local_reference/` 分别保存人工初值及两次处理结果。`candidate/map/` 是新的 ROLL 地图候选；`candidate/report.json` 记录来源、证据和限制，`candidate/changes.npz` 保存旧图删除候选点和保留的新采集特征点，后者可能与旧结构重合。`candidate/comparison.png` 和 `candidate/comparison_detail.png` 分别提供全图及变化区域的俯视对照。候选不会自动启用或覆盖源地图。应检查配准、变化点及独立定位表现，再决定是否使用。

定位使用与旧图对应的关联区域，并启用地图关联质量门控；自动区域包含未知空间，区域内仍需检查定位轨迹和匹配结果。当前实现按时间间隔累计射线证据，尚不能证明每个删除点都有不同视角支持；附近稳定回波可以阻止删除，但动态物体和错误配准仍可能影响结果。它只在旧图边界附近处理，不支持地图扩展或跨次时间戳重叠。静态环境地图、历史人工修改和 Agent 标注不会自动迁移；使用新地图导航前须单独处理并核对这些资产。

### 人工修正地图

```bash
bash scripts/edit_map.sh --static-map /path/to/static_map --out /path/to/new_static_map
bash scripts/edit_map.sh --localization-map /path/to/localization_map --out /path/to/new_localization_map
```

滚轮缩放，右键或中键平移；静态图可编辑空闲、占据与未知。静态编辑器默认勾选“拟合人工空闲缺失地面高度”，保存新地图时用邻近地面估算高度；取消勾选则不填充。也可以打开已保存的人工修正地图，在不再改占据的情况下勾选该项并另存新地图。拟合高度用于近似显示，人工空闲及拟合地面均不等于传感器实测；缺少足够参考点时程序拒绝保存。修改三维定位图会改变地图身份，需重新核对配套资产。

### 远程服务（Linux）

行人中心标注需要先在 Linux 上为已有索引的工程登记服务 ID、工程路径、读写权限和系统 ROS 解释器。配置格式见[标注服务示例](../configs/annotation_service.example.json)。将本机配置保存为 `configs/annotation_service.local.json`，激活检测环境后运行以下命令。将 `LINUX_TAILSCALE_IP` 换成本机的 Tailscale 地址。仅在本机使用时可省略 `--host`。

```bash
bash perception/scripts/serve_annotations.sh --config configs/annotation_service.local.json --host LINUX_TAILSCALE_IP
```

服务默认监听 8765 端口。Windows 客户端使用同一地址和已登记的工程 ID 打开工程。行人标注的缓存与同步见[检测训练](perception/技术实现-检测训练.md#远程标注与同步)。T1、T2 决策标注另有独立的[服务启动命令](decision/技术实现-VLM局部决策.md#决策任务标注)。

### Windows客户端

在解压后的客户端目录安装 `perception/detection_tracking/annotation/requirements-client.txt`，将地址和工程 ID 换为当前 Linux 服务：

```powershell
conda create -n social-nav-annotator python=3.11 pip
conda activate social-nav-annotator
python -m pip install -r perception/detection_tracking/annotation/requirements-client.txt
python -B -m perception.detection_tracking.annotation open --server http://LINUX_TAILSCALE_IP:8765 --project-id wheelchair
```

已有环境时跳过创建命令，避免覆盖。只读浏览加 `--read-only`。未同步草稿保留在客户端缓存，需等待服务器确认保存。

### 保存结果重跟踪
