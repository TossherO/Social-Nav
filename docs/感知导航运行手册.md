# 感知导航运行手册

本页集中维护操作命令。先按[准备](#准备)选择解释器，再从下表进入所需任务；各示例独立选用，不需要从头执行。日常流程直接展开，首次安装、ROS诊断和专项实验收在折叠块中。

当前以轮椅实机测试为主，已有环境正常时直接进入[RViz交互测试](#rviz交互测试)并沿用本机已验证配置。bag回放、部署自检和底盘探针按具体问题选择，不是每次试车前都要执行的流程。现场问题只在[实机清单](感知导航实机问题.md)维护，阶段结束后集中更新。

Linux命令默认从仓库根目录执行，Windows命令从客户端解压目录执行。路径占位符须替换为实际资源，新推理、导出和对照使用新结果目录；继续标注与恢复训练按相应小节操作。原bag、输入地图和旧推理结果保持只读。

## 准备

在模型环境中运行联合推理、检测预计算和训练。系统ROS解释器负责读取bag、原生定位和ROS工具，直接运行时会通过子进程调用它。先按本机记录替换下列三项：

```bash
PEOPLE_PYTHON=/path/to/project/env/bin/python
ROS_PYTHON=/path/to/ros/python3
GPU_ID=0
export CUDA_VISIBLE_DEVICES="$GPU_ID"
```

`GPU_ID`选择物理卡。RGB工具中的`--device 0`和跟踪中的`cuda:0`表示可见设备中的第一张卡。专用任务在各节声明自己的输入和输出；同一任务的连续步骤在同一终端执行。

<details>
<summary>首次运行或相关原生源码变化：构建直接运行时</summary>

已有兼容构建时跳过。先按目标设备设置CUDA编译器、兼容的主机编译器和计算能力，不照搬其他机器的值。

```bash
CUDA_COMPILER=/path/to/cuda/bin/nvcc
CUDA_HOST_COMPILER=/path/to/compatible/g++
CUDA_ARCH=86

SOCIAL_NAV_CUDA_ARCH="$CUDA_ARCH" CUDACXX="$CUDA_COMPILER" \
  SOCIAL_NAV_CXX="$CUDA_HOST_COMPILER" BUILD_JOBS=2 bash perception/scripts/build_runtime.sh
```

ROS诊断另按[对应构建步骤](archive/感知导航ROS诊断命令.md#ros诊断准备)准备，不需要为直接运行时构建全部catkin包。

## 日常运行与回看

常规推理使用`python -B -m runtime`；`perception/scripts/run.sh`调用同一入口。读取bag不需要ROS master，在线输入连接已有传感器。每条运行命令都包含定位、三维检测跟踪和局部环境更新，`--mode`只选择建图定位模式。默认使用GPU定位近邻、去畸变、三维检测、环境更新和DWA，IMU传播、原拟合与小矩阵仍在CPU上执行。

默认输出为不可执行的影子建议。交互入口另有显式实机模式，需要本车已确认参数、独占串口和人工使能，尚未完成实机验收。默认不加载YOLO或请求VLM；未提供目标时，记录感知结果与停车建议。

常规导航在计算繁忙时只保留最新待处理扫描和地图观察，不累积旧帧。`summary.json`中的`counts.source_scans`是源扫描数，`counts.scans`是实际进入检测的扫描数，`counts.maps`是发布的地图数；`scan_scheduling`和`map_scheduling`记录替换与失效丢弃。定位仍完整进入独立安全通道，所有年龄沿用测量时间。扫描归档、场景保存、决策输入记录或Agent观察使用顺序处理，负载与常规模式不同。当前地图始终生成原始距离场，详见[环境地图专题](perception/技术实现-环境地图与场景表示.md#栅格与坐标)。

当前地图采用整数高度计数和0.45局部自由门限。同帧可靠人物点由独立动态圆表示，未完成移交的短期人物证据仍保留0.2秒。`navigation_support`在有效地图关联下直接使用所选静态背景，不等待在线地面确认，并在地图线程生成GPU二维派生图。`environment_device`包含基础地图与二维支持，`safety_capsule_materialize`记录必要字段取回和场景准备；正常人物移交不增加整图上传，人物来源失配时才上传保守圆障碍图。原生地图保留显式跨流依赖，测速来源见[推理速度](感知导航推理速度.md)。更新源码后须按构建步骤重建环境CUDA库；当前库必须提供 `sn_occupancy_local_ground_conflicts` 和 `sn_navigation_support_with_ground_conflicts`，ROS显示消息必须包含 `EnvironmentGrid.ground_conflict`。部署自检会拒绝旧构建，不能继续混用。

### 选择传感器时钟会话

默认保留空间外参，直接使用传感器消息时间戳，`imu_time_offset`为零。启动不再收集30秒运动来估计时差，也不要求先声明已验证的时钟会话；FAST-LIO自身的重力、偏置与局部地图初始化仍正常执行。零偏移是运行默认值，不表示已经证明两台传感器严格同步。

已移除`--time-calibration`选项和自动估计步骤，旧命令需删去该选项及其值。需要固定补偿时，用`--lidar-imu-calibration FILE`选择有来源的配置。非零补偿仍记录会话适用范围，未知时给出提示，明确的会话不符则拒绝启动；配置错误、时间倒退及输入身份冲突仍按原规则处理。机制见[标定专题](perception/技术实现-建图与定位.md#雷达imu标定与同步实施策略)。

需要追溯设备会话时，按[采集步骤](#采集与bag处理)为bag保存记录；仅重新录包时沿用同一标识，相关设备或驱动重启后使用新标识。旧数据缺少记录时保持未知，不能根据文件日期补成已确认会话。正常零偏移运行不依赖这份可选记录。

如需显式固定补偿，选择保留空间外参的完整雷达—IMU标定YAML，记录时差、会话组和验证来源。已有`BAG.clock.json`时自动读取，例如：

```bash
BAG=/path/to/recording.bag
CALIB=/path/to/session_lidar_imu.yaml
OUT=outputs/perception/session_new

"$PEOPLE_PYTHON" -B -m runtime --bag "$BAG" --mode odometry \
  --lidar-imu-calibration "$CALIB" --output "$OUT/odometry" --gpu "$GPU_ID"
```

原 bag 目录只读时，先创建记录目录，再用记录工具的 `--out FILE` 将会话信息放到其他新文件，运行时通过 `--sensor-session FILE` 选择。工具使用项目已有的大小与边缘指纹核对 bag，复制或迁移同一输入后仍可使用；该指纹不是全文件摘要。显式传入的 `--sensor-clock-group GROUP` 若与 bag 记录冲突，会直接报错。live 输入只接受显式会话组，不使用 bag 记录，也不从旧运行继承设备会话。

`run.json`与直接runtime的`summary.json`保存`imu_time_calibration`，包括生效偏移、使用原时间戳还是固定补偿、会话来源及文件摘要；不会把启动记录写成重新校准成功。`--source-run`继续复用旧运行参数，包括旧偏移。要在旧运行几何上使用当前默认，应显式加`--lidar-imu-calibration perception/sensors/calibration/lidar_imu.yaml`。仅指纹相同的bag可以继承旧运行的输入会话；覆盖标定文件会清除旧标定的会话和验证声明。

### 从bag运行感知导航

**有图或混合定位。** 三维定位地图、人工起点和bag须对应。`LOCALIZATION_MAP`用于扫描配准，`STATIC_MAP`是供环境与导航查询的静态环境包，两者不能互换。缺少这些输入时先做[地图准备](#地图准备)。

```bash
BAG=/path/to/recording.bag
LOCALIZATION_MAP=/path/to/complete_3d_localization_map
POSE="${BAG%.bag}.initial_pose.json"
COVERAGE=/path/to/localization_coverage.yaml
STATIC_MAP=/path/to/static_environment_map
OUT=outputs/perception/session_new

"$PEOPLE_PYTHON" -B -m runtime --bag "$BAG" --mode localization \
  --map "$LOCALIZATION_MAP" --pose-file "$POSE" --coverage "$COVERAGE" \
  --static-map "$STATIC_MAP" --output "$OUT/localization" --gpu "$GPU_ID"
```

不使用手绘可信区域或静态环境先验时，分别省略`--coverage`或`--static-map`。有图关联撤销后，混合模式继续维护连续局部位置与局部环境地图。无图段不会自动探索，仍需明确的局部目标。

**无图定位与局部目标。** 目标为连续`odom`坐标系中的`base_link`位置，单位为米。

```bash
BAG=/path/to/recording.bag
OUT=outputs/perception/session_new

"$PEOPLE_PYTHON" -B -m runtime --bag "$BAG" --mode odometry \
  --goal 3 1 --goal-frame odom --output "$OUT/odometry" --gpu "$GPU_ID"
```

首次Ctrl+C请求停车并等待排空和保存。结束后查看`summary.json`中的成功或失败状态、帧数和阶段计时；地图与参数以同次`run.json`为准。失败时先读该运行的日志，参考搜索缓慢时看`reference.jsonl`中的`planning_timing_ms`和`search_attempts`。计量含义见[推理速度](感知导航推理速度.md)。

### 按录制路线生成分段目标

只有提供目标时才执行有效规划。`--coverage`负责撤销或恢复定位的地图关联，不会自行生成室外导航目标。已有带来源的演示路线时，可以显式启用bag影子回放：

```bash
ROUTE=/path/to/recorded_route.json

"$PEOPLE_PYTHON" -B -m runtime --bag "$BAG" --mode localization \
  --map "$LOCALIZATION_MAP" --pose-file "$POSE" --coverage "$COVERAGE" \
  --static-map "$STATIC_MAP" --route "$ROUTE" --route-floor floor1 \
  --start 0 --duration 367 --display --record-views \
  --output "$OUT/route_floor1" --gpu "$GPU_ID"
```

上例窗口对应10月29日一楼及室外段。该路线和各楼层地图需要另行准备；本机当前保留的二楼地图及环境路径见[本机记录](../ENVIRONMENT.local.md)。二楼另开运行，需选择与该路线、bag和起始偏移对应的地图、环境包、起点与可信区域。起点文件的偏移必须一致。

调度读取原bag的测量时间选择路线段，再根据当前位姿生成前视目标。室外使用离图前有效关联建立的局部锚点，返图后重新检查地图关联。`route.jsonl`记录选段、目标及暂停原因，`reference.jsonl`记录实际规划结果。原驾驶轨迹不会被作为本轮执行反馈。

该功能只用于同一原包的显式开发回放，不接受live，也不能与`--goal`或`--commands`同时使用。手动目标、取消或接管会停用路线调度。电梯段等待外部确认，两层分开运行，不根据录制时间宣告到层。机制见[路线回放](navigation/技术实现-任务与路线.md#录制行程的分段目标回放)。

### 选择运动配置

日常导航沿用[常规配置](../navigation/planning/configs/motion.yaml)，不传`--motion-config`时自动加载该文件。[激进配置](../navigation/planning/configs/motion_aggressive.yaml)保留10月20日两包对照中使用的较高运动限值，只作为后续调参的参考上限，系统不会因规划失败自动切换。常规配置不能满足实际需要时，再根据具体限制逐项调高，不必一次启用全部激进参数。

[低速试车配置](../navigation/planning/configs/motion_trial.yaml)用于本车受控试验，前进、倒车和角速度上限分别为0.10 m/s、0.05 m/s和0.20 rad/s。它是试验候选，不替换常规默认。实际使用时显式传入`--motion-config navigation/planning/configs/motion_trial.yaml`，并结合车辆档案核对运动、制动与响应假设；低速配置不会绕过使能或时效检查。加速度参数用于规划预测，底盘串口仍只接收速度目标。

要复查整套激进参数，在原runtime命令中显式追加：

```bash
--motion-config navigation/planning/configs/motion_aggressive.yaml
```

需要测试中间值时，复制常规配置为独立实验文件，显式增加或修改`max_forward_mps`等字段，再传入`--motion-config /path/to/motion.yaml`。该文件使用完整运动配置结构，不按`--runtime-config`的方式合并任意缺省项。参考规划、DWA和独立安全共用加载后的参数；`run.json`的`navigation_motion`记录配置来源及实际参数，开启规划记录时还保存在`planning/config.json`。

激进配置的数值来自录制运动估计和影子回放，不是实测车辆能力。制动减速度由对应加速度乘`brake_deceleration_scale`得到，提高加速度也会缩短模型制动距离；实机调高时须以实际制动能力为依据。常规与激进配置均保留停车、换向、输入时效和完整碰撞检查。

### 使用在线传感器

先完成[真实设备启动](#采集与bag处理)，保证外部master、点云与IMU运行。下面示例运行60秒无图定位：

```bash
OUT=outputs/perception/session_new

"$PEOPLE_PYTHON" -B -m runtime --live --mode odometry --duration 60 \
  --output "$OUT/live" --gpu "$GPU_ID"
```

有图在线任务改用`--mode localization`，并提供`--map`和明确的当前`--pose`；`--pose ROLL PITCH YAW X Y Z`的角度单位为弧度，位置单位为米。live不接受bag偏移、速率或起点文件。

真实设备使用正常ROS时钟。通过bag模拟在线传感器时，使用[外部回放命令](#外部bag回放)设置`/use_sim_time`并提供`/clock`，不要同时让同一master上的其他任务重复播放该bag。

### 复用旧运行重新推理

该入口复用旧几何、标定和原数据，重新计算定位与感知，不读取旧计算轨迹；执行后端采用当前默认。

```bash
RESULT=outputs/perception/previous_run
OUT=outputs/perception/session_new

"$PEOPLE_PYTHON" -B -m runtime --source-run "$RESULT" \
  --output "$OUT/recomputed" --gpu "$GPU_ID"
```

### 显示与提交目标

需要实时显示时，在所选运行命令中加`--display`。先启动或连接外部master，再在显示终端打开RViz；runtime只发布显示话题，不自行打开窗口。

```bash
source perception/scripts/ros1_env.sh
rviz -d perception/visualization/configs/runtime.rviz
```

默认RViz配置在连续`odom`坐标中显示三维点云和随地形起伏的导航图层。车体足迹和曲线采用对应位置的有效地面高度，不随一个固定的Z平面漂浮。只需定位和三维结果时，不必启用图像相关选项。

| RViz图层 | 显示内容 |
|---|---|
| `Navigation occupancy (terrain height)` | 导航实际使用的占据状态。浅灰为空闲，红色为占据，黄褐色为未知；静态自由支持及补充端点占据包含在内。缺少局部高度的静态支持格使用对应静态地面绘制，其余无有效高度的格子不绘制。 |
| `Terrain paths, vehicle and planning status` | 橙色车体地面投影历史、白色空间参考、青色DWA预测，以及车体轮廓、朝向和紫色意图目标。曲线不表示已经执行或获得执行许可。 |
| `Raw LiDAR path (3D diagnostic)`，默认关闭 | 雷达原点的原始三维历史，供定位诊断使用。 |
| `Navigation occupancy (XY diagnostic)`，默认关闭 | Z＝0的完整导航占据图，包括缺少可绘制地面高度的格子。 |
| `Raw local occupancy (XY diagnostic)`，默认关闭 | 补充静态自由支持前的基础局部占据图，用于对照。 |

默认地图和导航图层的话题为`/social_nav_runtime_view/ground_map`与`navigation`，扫描、人物和图像使用同前缀的`scan/people/rgb`。地图直接选用同一快照中的`navigation_occupancy`，没有静态支持派生层时使用`occupancy`；显示端不重新判定空闲。二维导航与基础图分别为`occupancy`和`raw_occupancy`。图层中的`REF/DWA`文字说明等待或拒绝原因，`GROUND`区分局部地面、静态支持高度和近车拟合，并给出曲线中有高度的采样点数量。规划可用但高度未知时，曲线会留出断口；未知高度不会补成Z＝0，也不会用线段跨接。历史点保留当时的高度，后续进入低处不会抬高或压低整条历史。

规划曲线过期、目标取消或定位失效时会清除；输入停止后也会检查到期，运行结束清除参考、预测和目标，历史仍可查看。DWA预测曲线的显示时效沿用[安全配置](../navigation/safety/config.yaml)的`max_input_age_s`，从原始反馈测量时间计算，不因重复显示刷新。真实的未知区域、运动约束或后台等待仍可能使规划不可用。辅助`path/reference/trajectory/lidar_path/occupancy`话题的内容与缺失处理见[显示接口](接口约定.md#可选显示与录制路线)。

镜头操作在三维点云区域进行。选择工具栏的`Move Camera`，或在该区域按`M`：左键拖动旋转，中键或`Shift＋左键`拖动平移，滚轮或右键拖动缩放。`Views`面板保持`Orbit`，也可直接调整`Yaw`、`Pitch`、`Distance`和`Focal Point`。RGB图像窗口不接受三维镜头操作。

显示频率由[运行时配置](../configs/runtime.yaml)的`display`独立维护：`scan_hz`、`people_hz`、`map_hz`、`rgb_hz`分别控制点云、人物、占据图和RGB，`navigation_hz`控制历史、参考、预测和状态。数值为墙钟Hz上限，设为0关闭该类别；消息仍使用原观察时间。

`height_mode: ground`为默认高度模式。`path_z_m: 0.03`表示历史和参考路径高于有效地面3cm；DWA、车体轮廓和朝向再分别抬高2、4、5cm，减少重叠闪烁。这些偏移仅用于显示。传感器盲区若缺少地面格子，可以在`ground_plane_radius_m: 1.5`限定的雷达周围范围内使用当前有效地面拟合，状态显示`fitted near vehicle`；设为0关闭这项显示补充。它不填充地图，也不参与导航放行。缺少有效高度时省略对应标记；需要检查固定平面投影时，可显式设置`height_mode: plane`，此时`path_z_m`表示绝对Z坐标。二维诊断时在RViz关闭`Navigation occupancy (terrain height)`，并启用`Navigation occupancy (XY diagnostic)`；该二维图使用RViz标准配色，白色为空闲、黑色为占据、灰色为未知。

参考路径表示到当前目标的空间路线。录制路线回放默认在约3m前方更新目标；DWA默认预测未来1.5s，轨迹长度随速度变化。历史和预测分别来自测量与运动预测，异步延迟可能使两者端点有小幅间隔。绘制规则与来源见[显示接口](接口约定.md#可选显示与录制路线)。

### 实机部署自检

先在轮椅计算机上选择本机解释器和GPU，并准备模型与一组相互对应的三维定位地图、静态栅格、可信区域和初始高度参考。`models/`、`outputs/`及本机覆盖配置不随Git同步；地图须复制完整目录，包括全部关键帧点云。检测扩展、runtime原生库与RViz插件按目标机器的Python、CUDA和ROS环境构建，不能把服务器可加载当作轮椅可用。构建步骤见本页[准备](#准备)。

运行只读自检，不要求ROS master，不加载模型权重做推理，也不打开串口或启动传感器：

```bash
source perception/scripts/ros1_env.sh
"$PEOPLE_PYTHON" -B -m runtime.preflight \
  --motion-config navigation/planning/configs/motion_trial.yaml --gpu "$GPU_ID"
```

输出JSON中的`checks`列出逐项结果，`assets`列出需要复制或本机构建的资源。`software_checks_passed=true`表示本次部署检查通过，退出码为0；失败返回1，应先处理`status=error`的项目。自定义地图使用`--config`，本机调度覆盖使用`--runtime-config`，后续交互运行须传入相同文件。GPU不可见时先核对设备权限、容器和调度，不直接重装依赖。自检检查库加载与必要符号，但不验证所有CUDA内核、模型精度、传感器在线状态或实时性能。

已有本车测量档案后，可追加执行条件检查。它仍然只读，不取得串口所有权，也不会使能：

```bash
"$PEOPLE_PYTHON" -B -m runtime.preflight \
  --motion-config navigation/planning/configs/motion_trial.yaml --gpu "$GPU_ID" \
  --execution-check --vehicle-profile /path/to/measured_vehicle.yaml \
  --chassis-port /dev/serial/by-id/ACTUAL_CONTROLLER
```

新机器部署或资源发生变化时使用本节自检；已有环境和现场条件正常时直接进入本次目标试验，不要求先重复影子观察、基本动作与逐项能力检查。沿用已有本车参数、停车和接管依据，只对本次异常或改变的条件补做对应检查。部署自检只核对软件资源，不表示实际目标已完成。

### RViz交互测试

`runtime.interactive` 负责起点选择、目标意图和bag播放控制，规划仍使用当前Hybrid A*、DWA与独立CPU安全。默认[交互配置](../navigation/planning/configs/interactive.yaml)选择10月20日二楼地图、对应静态环境包和人工可信区域；运动配置为常规档，激进档继续保留为显式试验选项。更换地图时，复制该配置并用 `--config` 指定相互对应的资产。

交互视图默认将静态底图绘制在建图地面高度，局部图使用当前地面高度。固定Z＝0的静态图保留为默认关闭的`Selected static map (XY diagnostic)`，避免遮挡实际地面。白色冻结参考路径和青色DWA使用各自坐标系中的地面高度，未知高度处断开；`Frozen terrain paths (preview only)`显示全部有高度的线段，两条默认关闭的`Path`诊断图层只显示连续前缀。文字以地面为高度参考并放到车体侧边，初始镜头也对准起点附近地面；本次视图配置保存在会话目录的`view.rviz`。显示高度缺失不会改变规划结果或生成虚构的地面。

位姿选择使用项目的`Ground Pose Estimate`和`Ground Nav Goal`工具。它们计算鼠标视线与所选静态地图有效地面格子的交点，支持斜视和俯视，不会拾取人物框或扫描点。没有地面高度或坐标系不匹配时不会提交。原生`2D Pose Estimate/2D Nav Goal`只在Z＝0取点，不适合此三维地面视图，因此项目默认工具栏不再加载它们。

首次部署或插件源码更新后，在仓库根目录单独编译显示插件；启动脚本不会自动编译，也不需要重建定位和导航原生库：

```bash
bash perception/scripts/build_ros1.sh visualization
```

先按[准备](#准备)设置模型解释器和GPU。终端一启动ROS master；传感器系统已有master时复用它，不重复启动：

```bash
source perception/scripts/ros1_env.sh
roscore
```

下面是服务器10月20日`localization2.bag`的离线示例。实机环境已正常时直接使用后面的`--live`入口，不要求先重复该bag。`--pose-file`会核对bag、地图、传感器帧和起始偏移，不能套用其他包或其他时刻。输出目录必须尚不存在：

```bash
BAG=data/datasets/wheelchair_rosbag/2026-10-20/localization2.bag
SOCIAL_NAV_PYTHON="$PEOPLE_PYTHON" bash perception/scripts/run_interactive.sh \
  --bag "$BAG" --pause-at 8 --gpu "$GPU_ID" \
  --pose-file outputs/perception/wheelchair_20261020/environment_integration/localization2.initial_pose.json \
  --output outputs/navigation/bag_preview_new
```

显式加载起点后，程序直接初始化，地图上的文字依次显示启动、定位及暂停状态。需要人工选起点时省略`--pose-file`；此时先显示静态地图和操作提示，尚未启动感知。只有配置中的起点文件与本次bag及偏移匹配时，才显示绿色起点箭头供参考，它不是当前定位结果。人工流程如下：

1. 用 `Ground Pose Estimate` 选择**雷达原点在地面的XY投影位置**，按住鼠标拖出朝向后松开。程序用它启动定位，再运行检测、地图和规划。选点是初值，不证明配准已经成功；需检查点云与静态图对齐及状态中的有效地图关联。
2. 用 `Ground Nav Goal` 选择车体目标位置及停车朝向。按下鼠标的位置是目标，拖动仅决定朝向，箭头尖端不是目标位置；方向拖动须对应至少5厘米，`Esc`取消未提交的操作。也可以用 `Publish Point` 点击可见地面，只选位置，让规划器决定朝向。目标必须在 `map` 坐标系中，每次选择替换上一次目标。`Accepted goal intent (not execution)`图层的紫色箭头尾部标出已接收目标，纯位置目标显示为紫色球；它不表示可达或已经执行，取消与播放阶段切换后会清除。
3. 终端输入 `p` 并回车暂停，输入 `r` 恢复，`s` 取消并撤销实机使能，`q` 保存退出。暂停后可以反复选目标；白线为冻结场景参考，青线为DWA预测，文字显示生成状态与失败原因。

地面位姿工具消息中的Z是所点地面的显示高度，不是雷达安装高度。定位初始化只采用所选XY和朝向；雷达地图高度和横滚、俯仰使用配置中同图起点文件作为初始猜测，必要时以 `--initial-z` 指定雷达高度。换起点或调整初始化时重新启动会话。目标位置对应 `base_link`，与初始化所选雷达原点不同。复用旧RViz窗口时须加载新会话的`view.rviz`，否则仍可能使用旧的Z＝0选点工具。

若初始化后仍只有静态地图，先看`Session instructions and localization status`图层。`MAP LOCALIZATION NOT ESTABLISHED`表示局部定位可能已运行，但尚未得到地图位姿；局部点云没有有效的`map→odom`变换，地图目标会返回`association_unavailable`。检查真实起点与朝向，或对匹配bag使用上述已保存起点。程序不会为了显示而伪造坐标变换。此时停止会话，再用新的输出目录重启；不覆盖原失败记录。

`--pose-file`仅用于对应bag，不能初始化实时轮椅，也不能与`--initial-z`混用。加载的是初始猜测，仍须由当前点云完成定位，不能将文件核验通过等同于本次配准成功。

`--pause-at` 是从本次第一帧扫描起算的源时间秒数，暂停落实到下一处完整扫描边界，并等待当前地图更新完成。`--start` 可以从bag内指定偏移开始初始化，但不能复用此前运行的隐状态；为保留历史地面与人物证据，通常从包头运行到待查时刻。当前没有向后拖动时间轴；换到更早位置需重启。包尾会保持暂停，允许继续选目标。

冻结预览在该场景的原始测量时刻计算，使用截止该时刻的定位历史估速；不会把车辆速度改为零，也不会刷新地图、人物或定位时间。它使用独立预览话题，不送给串口。恢复播放会撤销冻结目标与曲线，需要重新选目标。暂停源时间与实时安全超时是两件事，不能通过冻结预览让旧观察继续驱动车辆。

无交互终端时使用ROS服务；查看状态时可用 `rostopic echo /social_nav_interactive/state`：

```bash
rosservice call /social_nav_interactive/pause "data: true"
rosservice call /social_nav_interactive/pause "data: false"
rosservice call /social_nav_interactive/cancel "{}"
```

该命令只观察和规划。[本车档案](../configs/wheelchair_vehicle.yaml)记录了用户确认的车体轮廓及雷达到车体外参，也保存用户选择的试验执行参数。档案中的确认标志允许软件检查通过，但运动上界、制动、协议和失联停车仍包含未完成物理验证的假设；配置检查不代表这些假设已被证明。其他车辆从[通用模板](../navigation/control/vehicle.example.yaml)填写。现场实际状态和待核对项目见[实机问题](感知导航实机问题.md)。

本车的快捷入口及其配置纳入版本管理：先运行 `bash perception/capture/start_sensors.sh`，等待传感器就绪；再运行 `bash navigation/commissioning/start_observe.sh` 做在线观察。执行入口 `bash navigation/commissioning/start_execute.sh` 默认只打印命令，`--check` 只检查档案，显式 `--execute` 才启动带底盘出口的会话，仍需现场准备、选定当前起点并单独人工使能。两种入口从 `navigation/commissioning/interactive.yaml` 选择本机地图和关联范围，并从[性能配置](../navigation/commissioning/performance.env)读取7.5 Hz环境图目标频率、18米正方形局部环境图窗口和CPU 0—15性能核范围。窗口外没有局部观测支持，未知区域仍不能按空闲处理。通用运行入口保留模块默认窗口，`--environment-window-m` 可显式选择窗口，程序会检查其是否覆盖配置的地面拟合和导航支持半径。地图、模型和编译产物仍须在本机准备，路径和环境见[本机记录](../ENVIRONMENT.local.md)。

性能核范围通过 `taskset` 作用于观察或执行入口及其子进程，包括RViz、定位、规划和独立安全；单独启动的传感器驱动不受该限制。这是本机的CPU编号，迁移到其他计算机前须核对核心类型和允许的亲和范围，也可通过环境变量 `SOCIAL_NAV_COMMISSIONING_CPU_LIST` 指定已核对的CPU列表。无可用目标核心时入口会失败，不会自动换用其他核心。亲和性对真实运行的影响仍需现场验证，不能据此推断安全授权一定连续。

本车观察和执行入口都读取 `configs/wheelchair_vehicle.yaml`，使观察规划使用同一套车辆参数；观察入口仍不连接底盘。档案检查通过并不证明车辆运动和制动假设已完成物理验证。

车辆档案可用`stopping_model`增大`reaction_s`和`actuator_delay_s`，由DWA和独立安全监督共同使用；其他时效、心跳与输入有效性条件不随这两个模型预算变化。预算必须覆盖档案中的执行延迟及固件超时，不能把含爬升和位移门限的起步观测直接当作纯执行器延迟。未声明时沿用公共默认，声明值不能小于公共默认。

实际执行还须显式填写`controller`的`velocity_limit_field`、`feedback_max_linear_mps`和`feedback_max_angular_rps`，不能只确认协议名称。第一项是控制帧中的原始字段，其语义与取值须按本控制器核实，不由主机请求速度上限自动推定；后两项用于底盘反馈诊断，不能代替规划及串口写入的速度上限。已存在的实测档案升级时需补齐这组字段。自检会输出选中的停车预算和控制器字段，软件校验仍不等于实机确认。

真实执行档案还须填写`execution_response_bounds`：`max_planar_speed_mps`是车体参考点在适用工况下的实际平面速度上界，包含侧向运动；`max_stop_time_s`是停止非零指令或主动发零后到停稳的时间上界，须同时覆盖通信中断和主动发零，包含控制器响应与制动。角速度上界沿用档案的`max_angular_rps`。这些上界必须有本车来源，单次测试的请求速度、候选零速或停车确认时间不能直接充当保证值。已有档案需补齐这两个字段；检查不通过时不会启动实机输出。扩展范围可能使狭窄通道被拒绝，算法范围见[局部控制与安全](navigation/技术实现-局部控制与安全.md#实车接入边界)。

```bash
SOCIAL_NAV_PYTHON="$PEOPLE_PYTHON" bash perception/scripts/run_interactive.sh \
  --live --gpu "$GPU_ID" --vehicle-profile /path/to/measured_vehicle.yaml \
  --motion-config navigation/planning/configs/motion_trial.yaml \
  --execute --chassis-port /dev/serial/by-id/ACTUAL_CONTROLLER \
  --output outputs/navigation/interactive_live_execution
```

初始化后，先确认地图关联、现场通道和物理停车条件，再输入 `a` 并回车，或调用 `/social_nav_interactive/arm`，参数为 `data: true`。状态到达 `chassis.state=armed` 后才允许独立安全授权的指令下发。零速使能按旧驱动策略进行：19200波特率，静止且摇杆中立时从原始模式3切到1；取消、失联或退出恢复零速与模式3。摇杆接管、反馈异常和看门狗停车均要求重新人工使能。协议须由本车配置显式确认，不能把候选校验匹配当作固件验收。

每次输出的有效期限同时受轨迹、几何、定位反馈和独立安全心跳约束。串口进程独立于GPU和安全计算，接管与失联检查不依赖规划线程；最终断电和控制器失联保护仍由硬件负责。实机模式只接受实时输入，bag会在打开设备前拒绝执行选项。轮椅基本动作已有现场证据，完整目标导航仍待实机验证；服务器的软件、模拟与bag检查不替代真实到达和停车。

结果保存在会话目录：`initial_pose.json`记录选点初值，`command.json`记录实际命令，`runtime.log`记录运行信息，`run/preview.json`保存最后生成的冻结结果，`run/summary.json`报告退出状态。预览文件是历史产物，是否仍为当前结果以会话状态为准。

实机诊断集中在`run/chassis/`。`events.jsonl`连续记录实际串口写入的速度目标、收到的底盘反馈、安全授权及状态变化；授权中保留定位估速、原始源时间和拒绝原因。底盘没有测量时间戳，反馈时间明确为主机接收时间，不能直接与ROS测量时间相减，也不能将底盘上报值当作已验证运动真值。字段含义见[接口约定](接口约定.md#底盘诊断记录)。

先检查`telemetry_summary.json`的`finalized`与`complete`。只有二者均为true且无丢失、无错误，才表示记录完整；写盘堵塞时有界队列会丢记录，控制循环继续执行独立停车检查。未正常退出或强制结束可能只留下不完整记录，不据此计算完整制动指标。`status.json`只是驱动状态，超过0.5秒未更新时会话将其显示为不可用，不宣称车辆已停或任务到达。实际诊断按目标、下发、反馈和定位估速检查起步、转向、归零与超时，不只看规划是否生成。

### 底盘受控检查

该入口用于人工看护下的有界底盘协议检查，默认单次直行，显式选择后也可检查低速倒车或原地转向；它不启动自主导航。先确认轮椅原手柄能够正常电动行驶，检查主电源、充电状态及停车制动。不能仅因串口有反馈就认定驱动已使能。车体制动只按正常操作要求准备，不能解除物理停车保护来绕过故障。

没有台架时，需要平整空旷的场地、无人乘坐，以及能够直接操作物理停车开关的现场看护。先保持驱动禁用并让手柄回中，检查受限指令下是否仍静止；准备实际运动检查时，再明确核对驱动启用、停车制动和看护状态。任何异常都由现场人员立即停车，主机或系统故障不能只依赖脚本收尾。

下面命令只打印固定计划，不打开设备：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe
```

默认最高纵向目标为 0.03 m/s，角速度为零，发令窗口为 0.3 秒。每次可明确指定以下参数，超范围、非有限数和负值会在打开串口及创建输出目录前被拒绝。这些范围只是开发检查边界，不代表已经验证的硬件能力或安全速度。

| 参数 | 单位与范围 | 默认值 |
|---|---|---|
| `--speed` | 纵向目标上限，0.001～0.10 m/s。 | 0.03 m/s。 |
| `--pulse-s` | 包含起步爬升的发令窗口，0.1～3 秒。 | 0.3 秒。 |
| `--maneuver` | `forward`为前进，`reverse`为固定0.05 m/s倒车，`spin_left/spin_right`为原地转向。`--speed`仅用于前进。 | `forward`。 |
| `--angular-speed` | 仅用于原地转向的角速度大小，0.05～0.30 rad/s。左右符号由`--maneuver`决定，线速度保持零。 | 原地转向为0.10 rad/s。 |

例如，下列命令只打印 0.05 m/s、2 秒的计划，不连接设备：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe --speed 0.05 --pulse-s 2
```

将 `CHASSIS_PORT` 设为本机记录中已核实的串口别名，并选择一个尚不存在的输出目录后，才运行驱动禁用检查：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe \
  --port "$CHASSIS_PORT" --output outputs/navigation/ground_probe/inhibited_new --execute
```

实际运动检查需单独使用 `--motion` 并选择新的输出目录。例如，确认现场准备后，可运行一份涵盖起步与稳定段的计划：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe \
  --port "$CHASSIS_PORT" --output outputs/navigation/ground_probe/selected_new \
  --execute --motion --speed 0.10 --pulse-s 3
```

每次只执行所选的一份计划，不会因为没有响应就自动提高速度或延长发令时间。指令仍按原有加速度爬升，结束后发零并恢复原始模式 3；请求值与实际线上整数值均记录到结果中。收尾至少发零 1 秒，必要时最多等待 3 秒确认候选静止反馈。轻微起步偏转、稳定段平均偏转和较大瞬时偏转分别处理，持续偏转或较大的转向仍会中止。参数与独立进程保护见[实现说明](navigation/技术实现-局部控制与安全.md#受控地面底盘检查)。

需要对比更高的转向请求时，先打印例如0.20 rad/s、2秒的左转计划：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe \
  --maneuver spin_left --angular-speed 0.20 --pulse-s 2
```

实际执行仍需核对本次角速度与转动范围的现场准备，显式加入`--port`、新的`--output`及`--execute --motion`。右转用`spin_right`，不传负角速度。原地转向的单帧反向读数保留在日志中；只有反向角速度超过0.01 rad/s、持续至少0.20秒且包含至少3帧不同接收时间的反馈，才触发方向中止。正常方向或近零反馈会清除累计，反馈失效仍立即中止。这个判据用于避免短暂读数导致测试提前退出，不代表已验证传感器误差或真实转向方向。

输出的 `events.jsonl` 和 `feedback.bin` 保留指令与候选反馈，`result.json` 按起步、稳定与收尾阶段汇总，并区分序列完成、候选停车反馈和现场确认。没有观察到运动响应、出现异常转向或恢复失败时，保持停车并查明原因；不能把 `completed=true` 当作运动或任务成功。本入口不是原有影子速度话题的转发器。

#### 集中低速响应检查

需要一次采集多档起步响应、倒车和左右转向时，可选择固定六段计划，先打印而不打开设备：

```bash
/usr/bin/python3 -B -m navigation.control.response_probe
```

计划依次为前进0.01、0.03、0.06 m/s，倒车0.05 m/s，左右原地转向各0.10 rad/s，每段发令2秒，段间恢复零速与模式3并确认静止。前进0.10 m/s的既有有效记录可以复用，无需在该批次重复。上述数值只用于本次诊断，不是已验证的车辆限值。

本批次新增倒车和转向，获得明确授权后还需确认轮椅停稳、无人乘坐、手柄中立，前后及整车转动范围平整空旷、远离人员和楼梯，并保持物理急停看护。满足后执行：

```bash
/usr/bin/python3 -B -m navigation.control.response_probe \
  --port "$CHASSIS_PORT" --output outputs/navigation/ground_probe/response_selected_new --execute
```

六段动作在开始前固定。低速段若完整发令、无安全异常且已确认静止，但未观察到响应，会保留“无响应”结果，并按已授权计划进入下一段，不依据反馈改选速度。接管、模式异常、方向不符、反馈失效或停车未确认都会终止整个批次，不重试。每段原始指令与候选反馈分别保存，汇总记录是否完整执行、是否取得候选运动响应，不能把序列完成或候选反馈当作实机能力验收。该批次也不验证固件断发保护，车辆档案仍需有来源的参数与人工核对。

#### 固件断发停车检查

完成受控直行、自动归零和手柄接管检查后，可在相同现场条件下单独选择短时断发模式。它保持串口连接和反馈接收，只停止发送控制帧，用于观察固件是否在上位机补发零速之前产生停车反馈。按`Ctrl+C`会触发主动发零，不能代替这项检查；不要拔USB或关闭串口进程制造失联。

先打印本次固定计划，不打开设备：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe \
  --speed 0.10 --pulse-s 1.5 --silence-s 0.8
```

获得本次断发测试授权并确认轮椅停稳、无人乘坐、手柄中立、空旷场地和物理急停看护后，再执行一次：

```bash
/usr/bin/python3 -B -m navigation.control.ground_probe \
  --port "$CHASSIS_PORT" --output outputs/navigation/ground_probe/silence_selected_new \
  --execute --motion --speed 0.10 --pulse-s 1.5 --silence-s 0.8
```

程序先按既有条件检查并发令1.5秒，只有近期反馈显示确有前进、手柄中立且最后目标非零才进入断发。否则主动归零并中止，不能用静止轮椅证明失联停车。断发期限从最后一次实际串口写入计算，计划最多0.8秒；反馈、心跳及新观察均不能延长期限。此时仍可能按上一条速度目标运动，现场看护必须保持急停可用。

断发期间保留反馈有效性、手柄、速度和父进程心跳检查，允许固件自行从模式1退回模式3。若候选反馈在没有新控制帧的情况下满足连续静止窗口，提前结束观察；到期、反馈中断、接管、异常或人工取消时也会结束观察。之后只发送零速与模式3，不再次起步。若程序、主机或串口本身失效，软件无法保证恢复发零，仍须依靠现场物理停车。

`--silence-s`限定0.2～1.5秒，发令阶段至少1秒，两段合计最多3秒；参数在创建输出和打开设备之前验证。原有0.8秒示例不变；需要更长观察时可以在新的明确计划中选择发令1.5秒、断发1.5秒，不自动延长已选计划。

仅断发阶段中，小于等于0.03 m/s的反向反馈按连续0.20秒、至少3帧判断，短暂反向保留原始记录和累计次数；正常或近零反馈清除累计。超过0.03 m/s的反向仍立即中止，持续反向、过速、模式异常、接管和失联保护不变。主动发令阶段的纵向方向保护与静止确认门限不变。这项调整不把小读数默认当成噪声，也不把历史中止结果重记为通过。

`result.json`中的`silence_test.stationary_before_rescue`仅表示补发零速前是否取得连续静止候选反馈。未观察到时返回失败，并明确区分恢复零速后的停车；不能直接推断固件完全没有看门狗。现场观察还需确认轮椅确实停下。所有时间均为主机写入与接收时间，包含传输、制动和静止窗口，不是固件超时参数；程序始终保留`firmware_watchdog_verified=false`，不会自动填写车辆档案。

### 结果回看

查看器只读已有定位与`people.jsonl`，不重新推理。`RESULT`也可以指向完整三维地图目录。

```bash
RESULT=outputs/perception/previous_run

bash perception/scripts/view.sh --result "$RESULT"
```

按同刻原始扫描播放：

```bash
bash perception/scripts/view.sh --result "$RESULT" --play --points --rate 0.5
```

查看传感器坐标下的原生检测，包括缺定位时刻：

```bash
bash perception/scripts/view.sh --result "$RESULT" --play --points --frame lidar
```

可加`--start 5`跳到指定秒数，或加`--frame odom`查看连续局部轨迹。数据迁移后，用`--bag`和`--localization-map`指向同一原资产。

录制路线影子运行还可以生成逐控制周期的HTML审查页。运行目录须保留`control/reference/safety/route/localization.jsonl`及`run.json/summary.json`；页面区分参考可用、DWA候选生成和独立安全状态，并用同周期参考原因解释DWA等待。下面的命令只读日志，`--with-rgb`从同一bag提取过去的相机图像，不重新计算定位、检测或规划：

```bash
source perception/scripts/ros1_env.sh
"$PEOPLE_PYTHON" -B -m navigation.planning.timeline \
  --run "$RESULT" --output outputs/navigation/planning_timeline/session_new \
  --static-map "$STATIC_MAP" --with-rgb
```

输出目录必须尚不存在。无需地图背景时省略`--static-map`，无需图像时省略`--with-rgb`。直接在浏览器打开`review.html`，可拖动时间轴、逐周期查看、按原因筛选并导出审查意见。静态地图只作位置背景；旧日志没有保存的局部地图或规划曲线不会补画，也不把缺记录当作成功或失败。当前示例由[关键结果](感知导航总览.md#关键结果)索引。

需要检查行人点归属时，可用下方工具生成三维动态审查页。页面支持左键旋转、右键平移、滚轮缩放、逐帧播放、按人物聚焦及新旧归属对比；无需服务器或联网。Shift单击可选中原始点编号，在右侧填写意见后导出 `person_segmentation_review_answers.json`。橙色仅表示有效框内未归属的点，是否漏分须人工判断。

该页在两段冻结建图输入上重算当前人物归属，旧掩码沿用原记录，不重跑检测、定位或地图历史。它展示全部捕获点，但不是雷达全部原始回波，也不能把去除人物后的点云当作空闲地图。重建页面使用下面的命令；`--rgb-run`读取与捕获时间对应的成功路线回放配置，核对原bag摘要后只提取过去0.2秒内的图像，省略它可生成纯点云页面。

```bash
source perception/scripts/ros1_env.sh
"$PEOPLE_PYTHON" -B -m perception.environment.person_review \
  --capture-archive outputs/navigation/frozen_inputs/navigation_sources.zip \
  --capture-prefix outputs/navigation/map_control_root_cause/mapper_inputs \
  --rgb-run outputs/navigation/history/offline/background_person_navigation/run \
  --output outputs/navigation/person_segmentation_review_new
```

输出目录必须尚不存在。普通规划记录没有原始点与逐点掩码时，不能直接代替此处的捕获输入。浏览器须支持WebGL，未启用时页面会给出提示。

需要审查实际导航图与规划曲线时，在新的runtime影子运行中加`--record-planning`。它保持正常异步地图调度，在`planning/`保存控制周期对应信息、实际参考和DWA结果，平时约2Hz保存场景及查询输入。参考或当前车体足迹受阻、地面参考待确认或整体历史暂停，以及认证预算退出时，额外保存该次实际消费的场景，同一快照不重复写入；额外记录不会推迟原周期采样。仅有局部冲突标记不会强制逐图保存。队列有容量上限，结果须检查`summary.json`中的`planning_record.complete/dropped/error`。它不自动启用RGB或ROS显示，诊断复制与写入仍有开销，适合先做短片段。

上述HTML生成命令会自动读取这组记录，核对控制、场景和轨迹摘要后显示实际图层及曲线；没有对应场景快照时仍明确显示静态背景。紫色虚线表示保留但当前未就绪的参考，不是可执行路线。现场问题处理见[实机清单](感知导航实机问题.md)，旧对照只在离线归档中追溯。

只需检查生产、交接和消费延迟时，可单独加`--trace-timing`。它默认关闭，每个进程在内存中最多保留20000条事件，正常退出后写入`timing.jsonl`与`timing_input.jsonl`，不会开启图层归档或改变地图调度。启用静态支持时，其中的`navigation_support`还记录所选静态地面参考、关联状态和重置原因等有界元数据，不新增图层下载。核对同名`*.summary.json`中的`complete`和`dropped`，截断记录不能作为完整时序。异常终止可能没有写盘，不能据此认定阶段没有执行。时间字段区分主机单调时钟与原始测量时间，不能直接混减。

### 可选图像与决策输入

需要图像时，在所选runtime命令中增加对应选项。三项分别服务不同消费者：

| 选项 | 用途与输出 |
|---|---|
| `--record-views` | 约1Hz保存带RGB的完整场景。未启用时，`final_scene/`只保存最终几何和人物。 |
| `--agent-observations` | 约1Hz在后台准备Agent观察，不加载YOLO或请求模型，连接方式见[影子测试](decision/长程导航任务与评测计划.md#真实观察与runtime影子测试)。 |
| `--record-decision-inputs` | 对选中的三帧窗口运行YOLO与关联，保存`decision_inputs/`中的RGB、BEV、原身份、图像来源和PID映射，不调用VLM。 |

只有显示、场景归档、Agent观察或VLM准备被显式请求时才读取RGB。`--record-decision-inputs`不要求`--record-views`，但不能与`--no-image`合用。`--no-image`仅保留兼容，主流程本来就不加载YOLO。

历史不足、RGB过期或消费者忙时跳过窗口，不积压旧输入。准备失败记录在`run.json`的`decision_inputs.error/complete`中，不阻断主流程。图像支路共用GPU，可能竞争资源。旧安装数据须用`--camera-calibration MATCHING.yaml`指定匹配外参，协议见[VLM手册](decision/VLM部署与调用.md#直接运行时的三帧输入与响应接纳)。

## 地图准备

按`三维建图 → 选择起点和可信区域 → 导出静态环境地图`准备有图任务。三维定位地图用于点云配准，静态环境地图用于通行几何；可信区域是地图关联的有效范围，不是另一张地图。对象区别见[地图分类](perception/技术实现-环境地图与场景表示.md#地图与非地图对象)。

### 三维建图

独立建图使用 `build_map.sh`，以系统ROS Python读取bag，并直接调用原生FAST-LIO和ROLL。它不启动ROS master、传感器、检测或导航进程，默认沿用当前建图参数、标定和CUDA后端，需要已有兼容的定位原生库。此入口不依赖检测模型环境；解释器和动态库路径按本机记录配置。

```bash
BAG=/path/to/mapping.bag
OUT=outputs/perception/map_session_new

bash perception/scripts/build_map.sh --bag "$BAG" \
  --out "$OUT/mapping" --gpu "$GPU_ID"
```

程序按计算能力处理选定区间，不按1倍速等待。ROLL后台积压达到4帧时，前台暂停提交；不通过丢帧加速。原始测量时间保持不变，扫描计数不符、后台失败或长时间无进展会使本次运行失败。

成功结束后，完整三维地图位于`$OUT/mapping/map/`，`run.json`保存参数、输入指纹和时钟适用信息，`summary.json`保存计数及耗时。默认封存`environment/scans.sqlite`，供后续静态环境导出使用；本步骤不自动生成静态环境地图。`RUN`指运行目录，`LOCALIZATION_MAP`指其中的`map/`，两者不要混用。

程序成功只说明选定扫描已处理、地图已保存，不能证明地图几何正确。继续固定地图定位或导出导航先验前，应检查最终关键帧轨迹、同一平层的高度变化及重访墙面是否一致。发现倾斜或形变时保留原始结果并先排查，不用强制压平或放宽配准门限代替审查。

先检查短段时加`--duration 20`，或用`--start`选择其他起始偏移；结果会记录处理区间，不能当作整包建图。显式加`--no-record-scans`可省略扫描封存，但随后不能从该运行导出带射线自由证据的静态环境地图。CPU对照可同时传入`--lio-backend cpu --roll-backend cpu --deskew-backend cpu`。其他参数见`bash perception/scripts/build_map.sh --help`。

输出目录必须尚不存在。Ctrl+C取消运行并保留诊断文件，本次结果标记为未完成；失败或取消的运行不能交给静态导出器。需要完整地图时，用新输出目录重新运行，并用独立定位包验证地图适用性。联合感知导航仍使用`runtime`入口；需要ROS诊断时使用原有诊断入口。

只显示首帧点云与RGB并保存人工选点，不运行定位。起点文件必须对应当前bag、地图和起始偏移，工具拒绝覆盖已有标注。

```bash
bash perception/scripts/pick_start.sh --bag "$BAG" \

```

```bash

```

保存后，将该文件交给runtime的`--coverage`。已有区域的编辑与删除见[可信区域说明](perception/技术实现-建图与定位.md#手动地图可信区域与混合定位)。

### 静态环境地图

使用成功结束、完整封存扫描的建图运行。默认使用`geometric`复核，静态全图导出在CPU上执行。实时来源不传`--bag`，可选人物记录必须同源。

```bash
RUN=/path/to/mapping_run
STATIC_MAP=outputs/perception/environment_maps/scene_new

source perception/scripts/ros1_env.sh
"$ROS_PYTHON" -B -m perception.environment export --run "$RUN" --out "$STATIC_MAP" --export-pgm
```

如果`RUN`中已有`people.jsonl`，可直接在导出命令中加`--people "$RUN"`。bag迁移时可加`--bag /path/to/same_source.bag`，工具会核对原来源摘要。需要局部导出时加`--bounds XMIN YMIN XMAX YMAX`，省略则导出全图。

导出后检查并显示：

```bash
"$ROS_PYTHON" -B -m perception.environment query --static-map "$STATIC_MAP"
"$ROS_PYTHON" -B -m perception.environment view --static-map "$STATIC_MAP" --show
```

无桌面时，用`--out /tmp/environment_overview.png`替代`--show`保存图片。几何与裁剪查询见[环境查询](archive/感知导航ROS诊断命令.md#静态地图查询与场景重建)。

静态包不会随代码更新自动重建。查询摘要中的`ground_estimator`来自包内元数据，当前导出器记录为`per_cell_median_of_unique_ground_points`；`null`表示该包没有记录此项，不能据当前源码推断其生成算法。`free_recovery_policy`保留读取历史实验包的能力；当前导出器已撤回附加恢复逻辑，新包该字段为`null`。若旧包显示`visible_prefix_after_last_physical_hit_with_column_guard`，它仍包含实验恢复结果，源码回退不会改写其数组。核对时同时保留`source`、`snapshot_id`和包内配置。需要当前规则的新包时，用经过校验的历史扫描和位姿导出到新目录，再显式通过`--static-map`选择；不能只替换旧包图层或修改摘要。

## 标注与训练

### bag 行人中心标注

先预计算，再本机或远程复核，最后从Linux工程导出。多帧预计算先准备可靠离线定位；同一原始采集组可加入多个子包。工程保存模型来源与人工结果，换模型须新建工程。

**预计算。** 按需重复`--bag`添加子包，设备按本机资源选择。

```bash

bash perception/scripts/annotate_people.sh predict --bag "$BAG" --project "$ANNOTATION" \

  --pose-results "$POSE_RESULTS" \
  --root-group ORIGINAL_RECORDING --location-group LOCATION --split train
```

`POSE_RESULTS`按子包优先有图定位，其次无图定位。参数含义和来源分组见[训练专题](perception/技术实现-检测训练.md#rosbag人工中心复核与增量训练)。

**Linux本机标注。** 窗口中选择要处理的子bag。

可加`--sequence 子包文件名`指定初始序列，也接受完整路径或来源ID。`--sample-interval 1`显式设置一秒步长；省略时恢复各包设置，首次默认一秒。

`4`或“标记无人／空标注”将该帧保存为已标无人，拒绝范围内全部候选并清空中心，`Ctrl+Z`可撤销。绿色为已标有人，紫色为已标无人。其余状态、快捷键及核验语义见[标注操作](perception/技术实现-检测训练.md#标注操作)。

<summary>导出范围、位姿与图像配对选项</summary>

### 任务场景检测微调

先选择两张空闲卡，使用已准备的检测环境。当前新增采集默认全用于训练，历史验证仅用于遗忘与回归诊断，不是独立任务验收。完整三阶段训练和当前采样策略见[训练专题](perception/技术实现-检测训练.md#任务场景增量适配)。

下面每个子shell会进入仓库内SimpleDet3d副本，结束后当前终端仍在仓库根目录。先设置同一实验使用的变量：

```bash
TRAIN_ROOT="$PWD/perception/detection_tracking/training/simpledet3d"

RUN_TAG=task_scene_${MAX_SWEEPS}frame_new
```

**从导出数据准备新配置。** 可重复`--annotations`增加数据集，`--complete-only`仅用已标帧；已有准备好的配置时跳过。

```bash
(
  cd "$TRAIN_ROOT"
  "$PEOPLE_PYTHON" tools/task_scene.py prepare \
    --annotations data/wheelchair_det_extra/task_scene/annotations.json --location-group TASK_ROUTE \
    --out "$TRAIN_CFG"
)
```

**预览配置与权重选择。** 不读取训练样本、不创建输出，也不启动CUDA。

```bash
(
  cd "$TRAIN_ROOT"
  TRAIN_CFG="$TRAIN_CFG" MAX_SWEEPS="$MAX_SWEEPS" RUN_TAG="$RUN_TAG" DRY_RUN=1 \
    ./train_wheelchair_task_scene.sh
)
```

**正式训练。** `CUDA_VISIBLE_DEVICES`中的两张卡按当前资源调整。

```bash
(
  cd "$TRAIN_ROOT"
  CUDA_VISIBLE_DEVICES=0,1 TRAIN_CFG="$TRAIN_CFG" MAX_SWEEPS="$MAX_SWEEPS" RUN_TAG="$RUN_TAG" \
    ./train_wheelchair_task_scene.sh
)
```

新实验自动加载同帧数Stage 3最佳权重，已有实验目录优先恢复断点。更改标签、策略或时序时使用新实验名；完整恢复需保持同一输入和策略。

**与基线比较。**

```bash
(

)
```

默认输出距离分层和距离加权F1，无人帧仍统计误检，待标区域不作为背景。该比较使用配置中的历史验证来源，不等于新任务场景验收。


`PRETRAINED_MODEL`覆盖初始化权重，`CKPT`显式恢复完整状态。`EPOCH_SAMPLES`、`EPOCHS`与`BATCH_SIZE`未设置时沿用YAML，batch为每卡值。默认新增帧每轮全覆盖，旧帧轮内不重复、跨轮循环，`EPOCH_SAMPLES`只调整旧帧回放量。多帧实验修改`MAX_SWEEPS`并使用新实验名。

评估选项加在上面的`compare`命令中，并使用新的输出文件：

| 选项 | 用途 |
|---|---|
| `--diagnostic-training --datasets task` | 新标注训练集回代诊断。 |
| `--limit-per-dataset 12` | 少量样本检查。 |
| `--score-threshold 0.2` | 同时改变检测和评估阈值。 |
| `--max-recall-drop 0.02` | 示例容许值，仅在独立完整任务开发集上事先约定后使用。 |

完整入口参数见`train_wheelchair_task_scene.sh --help`。

## 采集与标定

### 采集与bag处理

以下命令使用已配置的系统ROS终端。真实采集先启动master和驱动，再录包；结束时先Ctrl+C停止录包，确认文件正常关闭，再停止驱动。

**终端1：启动master。** 已有master时跳过。

```bash
source perception/scripts/ros1_env.sh
roscore
```

**终端2：启动真实设备。** 序列号按实际设备填写。

```bash
source perception/scripts/ros1_env.sh
rosparam set /use_sim_time false
bash perception/scripts/start_sensors.sh --serial-front FRONT_CAMERA_SERIAL
```

相机默认以640×480、30 FPS采集彩色图像和深度图像，可加`--fps 15`降低帧率。后视相机可加`--rear --serial-rear SERIAL`，序列号也可由本机配置提供。`--lidar-only`不提供FAST-LIO所需IMU。

启动入口明确使用本仓库的传感器启动配置，避免复用旧驱动工作区时误加载同名launch文件。

本机配置`configs/perception.local.json`的`sensors.imu_sampling_reload`可为已有实测来源的相机启用每次启动采样重载。配置须指定SDK与USB序列号、固件、统一IMU话题、原设置和临时设置、预期频率及验证来源。入口先核对设备与固件，再临时切换IIO采样属性并恢复原值，最后检查实际频率、时间递增和发布者。临时属性值不直接表示赫兹，不能照搬到其他设备。未配置该处理、选择其他相机或仅启动雷达时，不执行重载。

启用后，等待终端提示“IMU采样重载完成……传感器已就绪”，再启动录包或定位。驱动开始输出后，重载与确认约需9秒；准备期间的消息仍保留原始时间，频率尚未确认。设备不匹配、恢复或确认失败时，入口报错并关闭自己启动的驱动，不反复重试或改写时间戳。该流程通过上述脚本、`python -m perception.sensors`和本机封装入口生效，直接调用ROS launch不执行此流程。

**终端3：录包。** 保留一份RGB与内参、原始点云、真实IMU及已有静态TF。

```bash
source perception/scripts/ros1_env.sh
OUT=outputs/perception/capture_new
mkdir -p "$OUT"

rosbag record --lz4 -O "$OUT/capture.bag" /rslidar_points /camera/imu \
  /camera/color/image_raw /camera/color/camera_info /tf_static
```

录制结束后，使用与本次设备连续运行对应的标识保存会话记录：

```bash
CLOCK_GROUP=lab_sensor_session_a
"$ROS_PYTHON" -B -m perception.sensors.clock_session \
  --bag "$OUT/capture.bag" --clock-group "$CLOCK_GROUP"
```

该命令创建 `capture.bag.clock.json`，不会覆盖已有记录或修改 bag。相同设备会话的其他 bag 使用同一 `CLOCK_GROUP`；设备或驱动重启后更换标识，并复核对应时差。记录是操作者对驱动连续性的声明，工具不监视 USB 重连或驱动重启；单包中若发生重启，应分段核实，不能用一个标识认定整包时差有效。不要仅修改标定的会话名称来消除不匹配错误，时差仍需独立验证。

查看bag及图形浏览；`rqt_bag`需已安装：

```bash
BAG=/path/to/recording.bag
rosbag info "$BAG"
rqt_bag "$BAG"
```

<details>
<summary>按相对时间切包并恢复缺失的静态TF</summary>

在系统ROS终端中执行。下例按原包记录时间切出`[10,20)`秒，输出新文件。

```bash
BAG=/path/to/original.bag
OUT=outputs/perception/cuts_new
mkdir -p "$OUT"
BAG_T0=$("$ROS_PYTHON" -c 'import rosbag,sys; b=rosbag.Bag(sys.argv[1]); print(b.get_start_time()); b.close()' "$BAG")

rosbag filter "$BAG" "$OUT/cut.bag" "$BAG_T0 + 10 <= t.to_sec() < $BAG_T0 + 20"
```

切包缺少`/tf_static`时，只能从原包恢复，工具不能生成不存在的标定。恢复脚本实际位置见本机记录。

```bash
TF_RESTORE=/path/to/restore_tf_static.py
SOURCE_BAG=/path/to/original_with_tf_static.bag

"$ROS_PYTHON" "$TF_RESTORE" --source "$SOURCE_BAG" \
  --input "$OUT/cut.bag" --output-dir "$OUT/cut_with_tf"
```
